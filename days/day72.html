The Evaluation Workflow

This is how we evaluate the LLM based application. We define the task and the target. We define success criteria. We build a dataset. We define an evaluation method. We run the model. We evaluate the result. We analyze. We improve the system. Then we go back and run again. It works in a loop. Once it is good enough, we deploy and monitor. If production fails, we go back to the dataset and repeat. The steps below are that loop. Later lessons open each step.

The loop

  1. Task and target What workflow? What task?
  2. Success criteria What does good mean? Which metric?
  3. Dataset The most important step. Real labeled rows.
  4. Eval method Automated, human, or another LLM.
  5. Run and score Send the dataset. Check the metric.
  6. Improve Change the prompt or the LLM. Run again.
  7. Deploy Ship, then monitor.
  8. Production failure If yes, add rows to the dataset and repeat.

Golden Dataset

The best option is we keep those 50 to 500 rows from real past conversations. That set is called a golden dataset, because it is real, from previous customer email. We do not invent the labels from a vibe test. We use what staff already routed. The cards below are why this set is golden.

Real

Rows come from previous conversations, not from made up prompts.

50 to 500

Enough rows to cover common cases and some edge cases.

Fixed labels

Each message has an expected label we trust.

975

Define an Evaluation Method

Then we define an evaluation method. There are multiple ways. Automated. Human. Or using a different LLM model. For this classification task we write Python and automate it. We do not need a human judge, and we do not need another LLM, just to check accuracy. The cards below are those three ways. We pick automated here.

Automated

Python compares predicted label to expected label. We use this.

Human

A person reads each answer and scores it.

Another LLM

A different model judges the answer. We do not need that for this accuracy check.

976

Run the Model

Run the model means we send the dataset through the LLM. Each input message gets a predicted label. We store that predicted label next to the expected label. We do not score by feel. We score in the next step. The steps below are that run.

One run

  1. Dataset Send every input message.
  2. LLM The model returns a predicted label.
  3. Log Keep expected and predicted side by side.
977

Evaluate the Result

Now we evaluate the result with Python. Count how many predicted labels match the expected labels. Divide by the number of rows. That is accuracy. The five rows below are a tiny demo of the golden shape. Four match. One miss. Accuracy is 80%. A real run uses 50 to 500 rows. The block below is that check. The first list is expected and predicted. The loop counts matches. Then we print the score.

Accuracy check

rows = [
    {"expected": "billing", "predicted": "billing"},
    {"expected": "technical", "predicted": "technical"},
    {"expected": "general", "predicted": "general"},
    {"expected": "billing", "predicted": "general"},
    {"expected": "technical", "predicted": "technical"},
]

correct = sum(1 for r in rows if r["expected"] == r["predicted"])
accuracy = correct / len(rows)
print(f"{correct} of {len(rows)} correct")
print(f"accuracy: {accuracy:.0%}")

What you get

4 of 5 correct
accuracy: 80%

Row 4 is the miss. Expected billing. Predicted general. Four matches out of five is 80%.

Analyze and Improve

Then we analyze the result. Look at the misses. In the demo, the invoice email should be billing, but the model said general. The main thing after that is to improve the system. Change the prompt. Or change the LLM. Then go back and run the model again. It works in a loop. The steps below are that improve cycle.

Improve

  1. Analyze Read the misses. Invoice went to general, not billing.
  2. Improve Change the prompt, or change the LLM.
  3. Run again Send the same dataset. Score accuracy again.

980

Production Failure

If there is a production failure, we go back to build a dataset and repeat the process. New real emails that failed become new golden rows. We run the loop again. Then we deploy the model again, and we monitor again. The steps below are that return path.

If production fails

  1. Failure Real emails are routed wrong, or users complain.
  2. New rows Add those emails to the golden dataset.
  3. Repeat Eval method, run, score, improve, then deploy and monitor.
