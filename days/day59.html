Day 59

LangSmith

LangSmith is an observability and evaluation tool. It stores an end to end trace of an LLM workflow so you can see each component, not only the final answer.

756

What is LangSmith

LangSmith is an observability and evaluation tool. Observability is the key word. It helps you see the internal working of a system, component by component. What input did this step take. What output did it give. That trace is stored, so you can open it later.

757

Why We Need LangSmith

We need it because LLM workflows are hard to debug. The three stories below are the same kind of problem. You see input, output, and total time. You do not see which step is slow, costly, or wrong.

Latency

The job usually takes 2 minutes. One day it takes 9 or 10 minutes. Which node is slow.

Cost

A caption usually uses 20 tokens. Some captions use 100 tokens. Why did spend jump.

Hallucination

A RAG bot gives a false leave policy. Was it the retriever or the model.

758

Latency in a Complex Workflow

We work in a startup. Students find a job on Recruit Nepal. They read the job description. They change the resume and the cover letter by hand, many times. That is slow. So we build an LLM app. The student uploads the job description and the resume. The model matches them. It writes a cover letter and proofreads it. Students like the tool. The flow below is that app.

JD and resume tool

  1. Upload Student sends the job description and the resume.
  2. Match An LLM matches the JD and the resume.
  3. Write The model prepares the cover letter and proofreads it.
  4. Cover letter The student gets the finished letter.

Normal latency is 2 minutes. One day many emails come. People say the site takes 9 or 10 minutes. We must find the root cause. The workflow is complex. It has many stages, branches, and more than one LLM, such as the JD match. We only have input, output, and total time. We cannot see which node is slow or broken. The issue might be this. Instead of scanning one folder in Google Drive, we scan every folder.

759

Cost When Tokens Jump

The first story was latency. This one is cost. We make a workflow that writes a caption. It usually uses 20 tokens. For some captions it uses 100 tokens. Same kind of app. The spend changes and we cannot see which step used the extra tokens.

760

Hallucination in a RAG Chatbot

We work at Google. A thousand freshers join. They do not know company rules, so they ask HR every day. HR is tired of the same answers. We build a RAG chatbot so people can ask and the bot can reply.

Then the bot hallucinates. A person asks what the leave policy is. The bot says there is no leave policy if you want that. That is big misinformation. A RAG system is very hard to debug. You only see the final answer.

761

Two Kinds of RAG Mistakes

Any RAG system can hallucinate in two ways. The table below is those two ways. It could be many small settings too. When we update the RAG we might set the retriever to 1 document. That is too low. It should have been 3 or 5. The prompt might be wrong. In the system message we must write, if you do not get the context, say I do not know, instead of making an answer. If we forget that line, the model invents. Debugging this hallucination is very hard.

Retriever Generator
The retriever fetches the wrong document. The docs are fine. A bad model, a bad prompt, or another LLM issue invents the answer.
762

Observability

The common part of the three stories is this. They are LLM workflows. The hardest part of an LLM system is that it is non deterministic. The same input can give a different output. That is very hard to debug. The problem does not leave a proper trace.

Observability helps you know the internal working of any system. You get an end to end trace. That trace is stored somewhere you can open later. LangSmith is the tool we use for this observability idea in our system.

763

What LangSmith Traces

LangSmith records more than the last line of text. The cards below are what a trace can hold.

Input and output

What went in. What came out. For the whole run and for each step.

Intermediate steps

What the retriever set. What it fetched. Each hop in the middle.

Latency

Time to output, at the component level as well as the whole run.

Token usage

Input tokens and output tokens.

Cost

Spend for that run.

Error

Where a step failed.

Tags

Labels you add so you can filter later.

Metadata

Extra facts you attach to the run.

Feedback

Signals you store with the trace.

767

RAG in Theory and Practice

A RAG app is this idea. You give a query plus context. You ask a personal question. You send the query and the relevant chunks from a document. The idea is simple in theory. In practice the quality is often not good enough.

RAG can have two issues. Retrieval issue: wrong or irrelevant docs are fetched. Generator issue: the retriever gave good text, and the LLM still hallucinates. In production we cannot say the answer is bad because of the retriever or because of the generator. We only get the final answer. LangSmith can show the user query, the retrieved docs, the LLM prompt with those docs inside, and the LLM response.

768

Trace a RAG Chain

This first RAG loads islr.pdf, splits it, builds a FAISS store, and answers from the PDF only. The project name is rag chatbot v1. The retriever uses similarity with k set to 4. The system line says answer only from the PDF context. If the answer is not found, say I do not know. RunnableParallel sends context from the retriever and the question through as is. LangSmith will see the chain hops that are LangChain runnables.

from dotenv import load_dotenv

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda
from langchain_core.output_parsers import StrOutputParser

os.environ['LANGCHAIN_PROJECT'] = 'rag chatbot v1'

load_dotenv()

OPENROUTER_API_KEY = os.getenv("OPENAI_API_KEY")

if not OPENROUTER_API_KEY:
    raise ValueError("OPENAI_API_KEY not found in .env file")

PDF_PATH = "islr.pdf"

loader = PyPDFLoader(PDF_PATH)
docs = loader.load()

print(f"Total pages: {len(docs)}")

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=150
)

splits = splitter.split_documents(docs)

print(f"Total chunks: {len(splits)}")

embedding = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2"
)

vectorstore = FAISS.from_documents(
    splits,
    embedding
)

retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 4}
)

llm = ChatOpenAI(
    model="openrouter/free",
    temperature=0.3,
    base_url="https://openrouter.ai/api/v1",
    api_key=OPENROUTER_API_KEY
)

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "Answer only from the provided PDF context. "
        "If the answer is not found, say I don't know."
    ),
    (
        "human",
        "Question: {question}\n\nContext:\n{context}"
    )
])

    return "\n\n".join(doc.page_content for doc in docs)

parallel = RunnableParallel(
    context=retriever | RunnableLambda(format_docs),

    parallel
    | prompt
    | llm

)

769

Two Problems in the First RAG

There are usually two issues here. The cards below are those two issues.

Not all steps are traces

LangSmith only traces LangChain runnables. The chain is tracked. PDF load, chunk, and embedding are not. The whole RAG app is not in one trace.

Latency grows

Each run loads the data, chunks it, and embeds it again. The more you run it, the longer you wait. The store should be saved and reused.

770

Traceable Setup Steps

For the first issue we wrap setup functions with the langsmith traceable decorator. LangSmith can only see LangChain runnables on its own. @traceable makes a normal function a run too. We name load_pdf, split_documents, build_vectorstore, and an umbrella setup_pipeline. The project name is rag chatbot v2. You can add tags and metadata on each decorator, such as metadata that says the loader is a pypdf loader. That is important. Each traceable decorator can take metadata and tags.

@traceable setup

from langsmith import traceable

os.environ["LANGCHAIN_PROJECT"] = "rag chatbot v2"

@traceable(name="load_pdf")
def load_pdf(path: str):
    loader = PyPDFLoader(path)
    return loader.load()

@traceable(name="split_documents")
def split_documents(docs, chunk_size=1000, chunk_overlap=150):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap
    )
    return splitter.split_documents(docs)

@traceable(name="build_vectorstore")
def build_vectorstore(splits):
    emb = HuggingFaceEmbeddings(
        model_name="sentence-transformers/all-MiniLM-L6-v2"
    )
    vs = FAISS.from_documents(splits, emb)
    return vs

@traceable(name="setup_pipeline")
def setup_pipeline(pdf_path: str):
    docs = load_pdf(pdf_path)
    splits = split_documents(docs)
    vs = build_vectorstore(splits)
    return vs

vectorstore = setup_pipeline(PDF_PATH)
retriever = vectorstore.as_retriever(search_type="similarity", search_kwargs={"k": 4})

config = {
    "run_name": "pdf_rag_query"
}

answer = chain.invoke(question, config=config)

FAISS.from_documents calls the embedding model inside build_vectorstore. The query still uses run_name pdf_rag_query.

v2 traces the functions, but it traces them as two separate things. Setup pipeline is one trace. The RAG query is another. What should happen is one RAG application with setup and the query in one structure. The later code wraps both under one parent named pdf_rag_full_run. That parent calls setup_pipeline, then the chain. The picture below is split traces versus one tree.

Cache the Index

Now we fix the latency issue. We save the FAISS index under .indices. A fingerprint of the PDF plus chunk settings plus the embedding model name becomes a folder key. load_or_build_index is not traced. It only picks a path. If the folder exists, load_index_run loads it. If not, build_index_run loads the PDF, splits, embeds, saves the store, and writes meta.json. setup_pipeline calls that dispatcher. setup_pipeline_and_query is the parent named pdf_rag_full_run. The project name is rag chatbot v4. The flow below is cache hit versus build.

Load or build

  1. Key Hash the PDF fingerprint, chunk size, overlap, and embed model.
  2. Cache hit load_index_run reads the saved FAISS folder.
  3. Cache miss build_index_run loads, splits, embeds, and saves.
  4. Query The parent run then asks the chain.

rag chatbot v4

import os
import json
import hashlib
from pathlib import Path
from dotenv import load_dotenv

from langsmith import traceable

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_openai import ChatOpenAI
from langchain_community.vectorstores import FAISS
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda
from langchain_core.output_parsers import StrOutputParser

os.environ["LANGCHAIN_PROJECT"] = "rag chatbot v4"

load_dotenv()

OPENROUTER_API_KEY = os.getenv("OPENAI_API_KEY")

if not OPENROUTER_API_KEY:
    raise ValueError("OPENAI_API_KEY not found in .env file")

EMBED_MODEL = "sentence-transformers/all-MiniLM-L6-v2"

PDF_PATH = "islr.pdf"
INDEX_ROOT = Path(".indices")
INDEX_ROOT.mkdir(exist_ok=True)

@traceable(name="load_pdf")
def load_pdf(path: str):
    return PyPDFLoader(path).load()

@traceable(name="split_documents")
def split_documents(docs, chunk_size=1000, chunk_overlap=150):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap
    )
    return splitter.split_documents(docs)

@traceable(name="build_vectorstore")
def build_vectorstore(splits, embed_model_name: str):
    emb = HuggingFaceEmbeddings(model_name=embed_model_name)
    return FAISS.from_documents(splits, emb)

def _file_fingerprint(path: str) -> dict:
    p = Path(path)
    h = hashlib.sha256()
    with p.open("rb") as f:
        for chunk in iter(lambda: f.read(1024 * 1024), b""):
            h.update(chunk)
    return {"sha256": h.hexdigest(), "size": p.stat().st_size, "mtime": int(p.stat().st_mtime)}

def _index_key(pdf_path: str, chunk_size: int, chunk_overlap: int, embed_model_name: str) -> str:
    meta = {
        "pdf_fingerprint": _file_fingerprint(pdf_path),
        "chunk_size": chunk_size,
        "chunk_overlap": chunk_overlap,
        "embedding_model": embed_model_name,
        "format": "v1",
    }
    return hashlib.sha256(json.dumps(meta, sort_keys=True).encode("utf-8")).hexdigest()

@traceable(name="load_index", tags=["index"])
def load_index_run(index_dir: Path, embed_model_name: str):
    emb = HuggingFaceEmbeddings(model_name=embed_model_name)
    return FAISS.load_local(
        str(index_dir),
        emb,
        allow_dangerous_deserialization=True
    )

@traceable(name="build_index", tags=["index"])
def build_index_run(pdf_path: str, index_dir: Path, chunk_size: int, chunk_overlap: int, embed_model_name: str):
    docs = load_pdf(pdf_path)
    splits = split_documents(docs, chunk_size=chunk_size, chunk_overlap=chunk_overlap)
    vs = build_vectorstore(splits, embed_model_name)
    index_dir.mkdir(parents=True, exist_ok=True)
    vs.save_local(str(index_dir))
    (index_dir / "meta.json").write_text(json.dumps({
        "pdf_path": os.path.abspath(pdf_path),
        "chunk_size": chunk_size,
        "chunk_overlap": chunk_overlap,
        "embedding_model": embed_model_name,
    }, indent=2))
    return vs

def load_or_build_index(
    pdf_path: str,
    chunk_size: int = 1000,
    chunk_overlap: int = 150,
    embed_model_name: str = EMBED_MODEL,
    force_rebuild: bool = False,
):
    key = _index_key(pdf_path, chunk_size, chunk_overlap, embed_model_name)
    index_dir = INDEX_ROOT / key
    cache_hit = index_dir.exists() and not force_rebuild
    if cache_hit:
        return load_index_run(index_dir, embed_model_name)
    else:
        return build_index_run(pdf_path, index_dir, chunk_size, chunk_overlap, embed_model_name)

llm = ChatOpenAI(
    model="openrouter/free",
    temperature=0.3,
    base_url="https://openrouter.ai/api/v1",
    api_key=OPENROUTER_API_KEY,
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer ONLY from the provided context. If not found, say you don't know."),
    ("human", "Question: {question}\n\nContext:\n{context}")
])

def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

@traceable(name="setup_pipeline", tags=["setup"])
def setup_pipeline(pdf_path: str, chunk_size=1000, chunk_overlap=150, embed_model_name=EMBED_MODEL, force_rebuild=False):
    return load_or_build_index(
        pdf_path=pdf_path,
        chunk_size=chunk_size,
        chunk_overlap=chunk_overlap,
        embed_model_name=embed_model_name,
        force_rebuild=force_rebuild,
    )

@traceable(name="pdf_rag_full_run")
def setup_pipeline_and_query(
    pdf_path: str,
    question: str,
    chunk_size: int = 1000,
    chunk_overlap: int = 150,
    embed_model_name: str = EMBED_MODEL,
    force_rebuild: bool = False,
):
    vectorstore = setup_pipeline(pdf_path, chunk_size, chunk_overlap, embed_model_name, force_rebuild)
    retriever = vectorstore.as_retriever(search_type="similarity", search_kwargs={"k": 4})

    parallel = RunnableParallel({
        "context": retriever | RunnableLambda(format_docs),
        "question": RunnablePassthrough(),
    })
    chain = parallel | prompt | llm | StrOutputParser()

    return chain.invoke(
        question,
        config={"run_name": "pdf_rag_query", "tags": ["qa"], "metadata": {"k": 4}}
    )

if __name__ == "__main__":
    print("PDF RAG ready.")

    while True:
        question = input("\nQ: ").strip()

        if question.lower() in ["exit", "quit"]:
            break

        if not question:
            continue

        answer = setup_pipeline_and_query(PDF_PATH, question)
        print("\nA:", answer)

load_or_build_index has no decorator. The child runs are load_index or build_index. The parent is pdf_rag_full_run.

When the Index Rebuilds

The cache key changes, so a new index is built, in these cases. The list below is those cases.

  • No cache exists yet. This is the first ever run.
  • PDF content changes. The sha256 in the fingerprint changes.
  • PDF file metadata changes, such as size or mtime.
  • Chunk params change. Chunk size or chunk overlap.
  • The embedding model name changes.

The same env tracing works for an agent. The project name is agent. We pull the ReAct prompt from the LangChain Hub with Client().pull_prompt. We add a line so the agent waits for the tool result and does not write Observation itself. AgentExecutor wraps the agent. Tools are DuckDuckGo search and a weather tool. Put the weather key in an env var. Do not paste a live key in code. agent project

import os
import requests
from dotenv import load_dotenv

from langchain_groq import ChatGroq
from langchain_core.tools import tool
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_classic.agents import create_react_agent, AgentExecutor
from langsmith import Client

os.environ["LANGCHAIN_PROJECT"] = "agent"

load_dotenv()

if not os.getenv("GROQ_API_KEY"):
    raise ValueError("GROQ_API_KEY not found in .env file")

search_tool = DuckDuckGoSearchRun()

@tool
def get_weather_data(city: str) -> str:
    """
    This function fetches the current weather data for a given city
    """
    url = (
        "https://api.weatherstack.com/current"
        f"?access_key={os.getenv('WEATHER_API_KEY')}&query={city}"
    )

    response = requests.get(url)
    response.raise_for_status()

    return str(response.json())

llm = ChatGroq(
    model="openai/gpt-oss-120b",
    temperature=0,
)

prompt = Client().pull_prompt(
    "hwchase17/react",
    dangerously_pull_public_prompt=True,
)
prompt.template += (
    "\nAfter Action Input, stop. Do not write Observation yourself. "
    "Wait for the tool result, then write Thought and Final Answer.\n"
)

agent = create_react_agent(
    llm=llm,
    tools=[search_tool, get_weather_data],
    prompt=prompt
)

agent_executor = AgentExecutor(
    agent=agent,
    tools=[search_tool, get_weather_data],
    verbose=True,
    max_iterations=5,
    handle_parsing_errors=True,
)

response = agent_executor.invoke({"input": "What is the current temp of gurgaon"})
print(response)

print(response['output'])

More Than Observability

Today we mainly learned observability. LangSmith has more. The cards below are those other parts. They are used a lot in production.

Monitoring and alerting

Set an alert. Watch traces. If too many requests come at once, you can cut them. If latency rises across many traces, that is a problem.

Evaluation

LLMs are non deterministic. A prompt change or a model change can give a new answer. Measure on a standard dataset. LLM as a judge is a common example. Use a pre built evaluator or make your own. This sits under LLM Ops.

Prompt experiments

Test and compare prompt versions in a systematic way. Run an A B test. There is a prompt engineering section and a playground.

Datasets and annotation

Build a dataset for evaluation and fine tuning. Support manual annotation. Store the dataset.

User feedback

Capture up and down, a rating, or structured feedback from users in production.

Collaboration

Copy the link of a trace and share it with the team.

Day 59 takeaways

Day 59 takeaways

  • LangSmith is an observability and evaluation tool for LLM workflows.
  • Latency, cost, and hallucination are hard to debug when you only see input, output, and total time.
  • RAG can fail in the retriever or in the generator. You need the middle steps to know which one.
  • LLM systems are non deterministic. The same input can give a different output. A stored end to end trace helps.
  • A project holds many traces. One execution is a trace. Each component that runs is a run.
  • LangSmith traces input, output, middle steps, latency, tokens, cost, errors, tags, metadata, and feedback.
  • Use a new LANGCHAIN_PROJECT name for each app. Add run_name, tags, and metadata on invoke.
  • LangSmith traces LangChain runnables. Use @traceable for load, split, and embed. Prefer one parent run.
  • Save the FAISS index. Rebuild when the PDF, chunk settings, or embed model change.
  • Agents and LangGraph nodes show up as runs. Monitoring, evaluation, prompt tests, datasets, feedback, and share links are the rest of the product.
