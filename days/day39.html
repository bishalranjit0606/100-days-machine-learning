Bring AI to the Public

When we want the public to use AI, we do it with an API. FastAPI is the framework we will use.

Many YouTube FastAPI videos teach it from a software view. We will learn it from an ML view: how a model reaches real users.

We will cover FastAPI in three parts. This is the map.

Three parts of FastAPI

  1. Fundamentals What an API is, why we need it, and how it talks over the internet.
  2. API for an ML model Wrap a trained model so other apps can call predict.
  3. Deploy on AWS Put the API on AWS, Amazon Web Services, so the public can reach it.
547

What Is an API

An API lets two software pieces talk. The usual pair is the frontend and the backend. The API is the connector between them.

A restaurant makes this easy to see. The customer is the frontend. The kitchen is the backend. The waiter is the API.

Customer, waiter, kitchen

  1. Customer Frontend. Asks for food.
  2. Waiter API. Carries the order to the kitchen.
  3. Kitchen Backend. Cooks the food.
  4. Waiter again Brings the food back, plated in a format. That format is JSON.

The customer never walks into the kitchen. The waiter takes the request, the kitchen works, and the waiter returns the result.

548

Life Without an API

Picture a flight booking site. You only want to see how many flights there are. Data moves like this: database, then backend, then frontend. The frontend is wired straight to the backend. You can build that without an API.

Without an API, frontend and backend live in one application. That is monolithic architecture. It can work. The cost is tight coupling. If one piece has a problem, it can hit the whole website.

This table puts a monolith next to an API.

Monolithic With an API
Frontend and backend sit in one app. Frontend, backend, and API are separate pieces.
One issue can affect the whole site. The site is not locked to one coupled block.
The backend is not an independent piece you can share. Other apps can talk to the backend through the API.
549

Why Partners Need an API

Now suppose companies like Trip.com or Yatra want your flight data and will pay for it. The hard part is how to give it to them.

One technical answer is to open the database. That is unsafe. They might change or harm the data. The safer path is to let them reach the backend, not the database.

In a monolith the backend is not an independent piece, so you cannot share that way. That is a real restriction. The site will not let you hand the database to a partner.

So we stop using monolithic architecture. Frontend is separate. Backend is separate. Partners talk through an API. This flow is the safe way to share data.

Safe share of data

  1. Partner Trip.com, Yatra, or Make My Trip asks for data.
  2. API Public door. Checks the request before it goes further.
  3. Backend Reads what is allowed. The partner never touches the database.
  4. Database Stays private. Only the backend talks to it.
550

The API Sits in Front

An API is a function, but it is a function that lives on the internet. In that sense it is public. Anyone can try to call it.

The backend itself is not placed directly on the internet. With an API, the backend becomes reachable through that public door.

You can put security on the API. It can check for malicious data before anything reaches the backend.

The frontend is not special. A caller gets the same data the sender put on the API. There is no private extra feed just because the screen is yours.

The second problem an API fixes is protocol. Everyone on the internet must follow the same rules so the message is understood.

551

HTTP and JSON

Because this all happens on the internet, the API follows the HTTP protocol. The data format it uses is JSON.

JSON works in every common language. Make My Trip, Yatra, or another partner might be in Python, Java, or something else. We need a format every language can read. JSON is that universal data format.

JSON looks a lot like a dict in Python. Same idea: keys and values. The two sides of this block show that likeness.

JSON

{"dish": "tea"}

Python dict

{"dish": "tea"}

Same shape. JSON is the text. A Python dict is what you use in code.

552

One Backend, Many Frontends

Around the year 2000, a website was no longer enough. A company needed a website, Android, and Apple. Each app was on a different stack. Three apps are hard to keep in sync. They are independent. If a comment changes on the website, Android and Apple need that change too.

The fix is to leave the monolith and use an API based architecture. Instead of three databases, use one. You still have three frontends. When they need data, they all talk to the same backend through the API.

Here the three frontends share one API.

Three frontends, one backend

  1. Website One frontend.
  2. Android Second frontend.
  3. Apple Third frontend.
  4. Same API All three ask the same backend and the same database.
553

How APIs Help ML

In software, the important store is the database. It holds the data. In machine learning, deep learning, and Gen AI, the important piece is a model that is ready for the real world.

ChatGPT is the example. OpenAI built it. It is powered by a GPT model. They train the model. To let people use it, they put a website in front.

The path looks like this. You train the ML model. You store it in a binary format. You load it in a programming language. That load and the predict function are the backend. The frontend talks to that backend.

This table is the software view next to the ML view.

Software view ML view
API to backend to database. API to backend to model.
The database holds the data. The model holds the trained skill.
Partners pay for data access. Companies want the model, for RAG or other apps.

If the website, the predict code, and the model all sit in one folder, that is still a monolith. When ChatGPT launched, people wanted access to the model. Companies wanted it for RAG. You cannot hand them the backend. That is why the API sits in front.

The chain is LLM, then backend, then API, then companies or users. The only change from the software picture is this: instead of a database we use the LLM. That is the ML perspective.

The same API can serve a website, Android, Apple, or any app that needs the model.

This chain is how a model reaches the public.

Model to the public

  1. LLM The trained model, stored in binary form and loaded for predict.
  2. Backend Runs predict. Stays off the open internet.
  3. API Public door for companies and users.
  4. Apps Website, Android, Apple, or any client that needs the model.
