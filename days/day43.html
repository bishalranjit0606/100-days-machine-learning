Day 43

Pydantic

Python lets any type into a variable. Pydantic checks the shape, the types, and your rules before the data reaches your functions.

587

Python Types Are Dynamic

Python is not a static type language. It uses dynamic types. When you create a variable, you can store any kind of data in it. That is good for a beginner. In production it is a problem. Bad data can reach a database, an API, or a model.

Pydantic helps you validate data and give it a structure. Teams use it in FastAPI, with YAML configs, and in ML pipelines.

The table below is beginner Python next to production.

Dynamic Python Production need
A variable can hold an int, a string, or anything else. Age must be an int. Email must look like an email.
Easy to start. Wrong values must stop before they are stored.
588

Any Value Can Slip In

Suppose we write a function to insert a patient. The age parameter can receive 30, the string "30", or the word thirty. Python still runs. As programmers it is our duty to stop that.

No type checks

def insert_patient_data(name, age):
    print(name, age)
    print("inserted into the database")

insert_patient_data("john", 30)
insert_patient_data("jane", "30")
insert_patient_data("ram", "thirty")

Output

john 30
inserted into the database
jane 30
inserted into the database
ram thirty
inserted into the database

All three calls succeed. The function does not care what age is.

589

Type Hints Only Suggest

We can add type hints: name: str and age: int. That only suggests the types. It does not force them. Wrong values still run. Python does not raise an error from the hint alone.

Hints, still no force

def insert_patient_data(name: str, age: int):
    print(name, age)
    print("inserted into the database")

insert_patient_data("john", 30)
insert_patient_data("jane", "30")
insert_patient_data("ram", "thirty")

Output

john 30
inserted into the database
jane 30
inserted into the database
ram thirty
inserted into the database

The hints help your editor. They do not stop bad age values at runtime.

590

Manual Checks Do Not Scale

We can write if type(name) == str and type(age) == int. That works for one function. It is not scalable. An update function needs the same checks again. If we add weight, or more functions, we copy those lines by hand.

Age also must not be negative. Then we add another rule, like age greater than 0. For these small rules we write long code. Pydantic is built to take that job.

Hand written checks

def insert_patient_data(name, age):
    if type(name) == str and type(age) == int:
        print(name, age)
        print("inserted into the database")
    else:
        print("invalid data")

insert_patient_data("john", 30)
insert_patient_data("jane", "30")

def insert_patient_data_age(name, age):
    if age > 0:
        print(name, age)
        print("inserted into the database")
    else:
        print("invalid data")

insert_patient_data_age("john", 30)
insert_patient_data_age("jane", -30)

Output

john 30
inserted into the database
invalid data
john 30
inserted into the database
invalid data

Each new field or new function means more if lines. That is the pain Pydantic removes.

591

Three Steps in Pydantic

Pydantic works in three steps. First you make a model class. You list the fields, their types, and rules such as greater than 0. Second you make a dict or JSON like structure. When you build the model, that data is checked. Third you pass the valid model object into your function.

Install Pydantic v2. v2 is written in Rust and has newer features.

Model, data, then function

  1. Model A class with fields, types, and rules.
  2. Dict or JSON Pydantic checks this data when you build the object.
  3. Function Pass the valid object. The function can trust it.

Install, then the three steps

pip install pydantic

from pydantic import BaseModel

class Patient(BaseModel):
    name: str
    age: int

patient_info = {
    "name": "john",
    "age": 30
}

patient = Patient(**patient_info)

def insert_patient_data(patient: Patient):
    print(patient.name, patient.age)
    print("inserted into the database")

insert_patient_data(patient)

Output

john 30
inserted into the database

**patient_info unpacks the dict into name and age. If age were a bad type, Patient(...) would fail before the function runs.

Optional Fields

Some fields are not always present. Import Optional from typing. Give a default. If the dict has no allergies, Pydantic fills None. Here married defaults to False.

Defaults fill the gaps

from pydantic import BaseModel
from typing import Optional

class Patient(BaseModel):
    name: str
    age: int
    city: str
    gender: str
    height: float
    contacts: dict[str, str]
    allergies: Optional[list[str]] = None
    married: Optional[bool] = False

patient_info = {
    "name": "john",
    "age": 30,
    "city": "New York",
    "gender": "male",
    "height": 180.5,
    "contacts": {
        "email": "john@example.com",
        "phone": "1234567890"
    }
}

patient = Patient(**patient_info)
print(patient.name)
print(patient.age)
print(patient.city)
print(patient.gender)
print(patient.height)
print(patient.married)
print(patient.allergies)
print(patient.contacts)
print(patient)

Output

john
30
New York
male
180.5
False
None
{'email': 'john@example.com', 'phone': '1234567890'}
name='john' age=30 city='New York' gender='male' height=180.5 contacts={'email': 'john@example.com', 'phone': '1234567890'} allergies=None married=False

EmailStr and AnyUrl

For common shapes like an email or a link, Pydantic already has types. EmailStr checks an email. AnyUrl checks a URL, such as a LinkedIn link. Install with pip install "pydantic[email]" so EmailStr works.

If married and allergies are missing, and both default to None, Pydantic fills None for each.

EmailStr

from pydantic import BaseModel, EmailStr
from typing import Optional

class Patient(BaseModel):
    name: str
    age: int
    city: str
    gender: str
    height: float
    contacts: dict[str, str]
    email: EmailStr
    allergies: Optional[list[str]] = None
    married: Optional[bool] = None

patient_info = {
    "name": "john",
    "age": 30,
    "city": "New York",
    "gender": "male",
    "height": 180.5,
    "contacts": {
        "email": "john@example.com",
        "phone": "1234567890"
    },
    "email": "john@example.com"
}

patient = Patient(**patient_info)
print(patient.married)
print(patient.allergies)

Output

None
None

For a URL field, import AnyUrl and type the field as AnyUrl. Same idea as EmailStr: a common format, checked for you.

Field and Annotated

The second way to validate is custom rules. Age might need to sit between 40 and 50. Use Field. gt means greater than. lt means less than. A string can have min length and max length. A list can too. In Pydantic v2 those list limits are min_length and max_length.

Field also stores metadata for APIs. The docs can show a description and an example. Wrap the type with Annotated. Field can set a default as well, such as married False.

The sample below uses age 45 so it passes gt=40 and lt=50. Age 30 would fail that rule.

Annotated plus Field

from pydantic import BaseModel, Field
from typing import Annotated

class Patient(BaseModel):
    name: Annotated[str, Field(min_length=3, max_length=50, description="Name of the patient", examples=["John Doe"])]
    age: Annotated[int, Field(gt=40, lt=50, description="Age of the patient")]
    city: Annotated[str, Field(min_length=3, max_length=50, description="City of the patient", examples=["New York"])]
    gender: Annotated[str, Field(min_length=3, max_length=50, description="Gender of the patient", examples=["Male"])]
    height: Annotated[float, Field(gt=150, lt=200, description="Height of the patient")]
    allergies: Annotated[list[str], Field(min_length=1, max_length=5, description="Allergies of the patient")]
    married: Annotated[bool, Field(default=False, description="Marital status of the patient")]

patient = Patient(
    name="John Doe",
    age=45,
    city="New York",
    gender="Male",
    height=180.5,
    allergies=["Penicillin"],
    married=False
)
print(patient)

Output

name='John Doe' age=45 city='New York' gender='Male' height=180.5 allergies=['Penicillin'] married=False

Field Validator

A field validator is for your own business rules, or for a change to the value. Example: the hospital ties up with a bank. An IME employee gets discounted treatment. The email domain must be ime.com or everest.com. Another example: turn the name so the first letter is a capital.

Email domain and name

from pydantic import BaseModel, field_validator

class Patient(BaseModel):
    name: str
    age: int
    city: str
    gender: str
    height: float
    allergies: list[str]
    married: bool
    email: str

    @field_validator("email")
    @classmethod
    def validate_email(cls, value: str) -> str:
        valid_domains = ["ime.com", "everest.com"]
        domain = value.split("@")[-1]
        if domain not in valid_domains:
            raise ValueError(f"Invalid email domain: {domain}")
        return value

    @field_validator("name")
    @classmethod
    def validate_name(cls, value: str) -> str:
        return value.capitalize()

patient_info = {
    "name": "john doe",
    "age": 30,
    "city": "New York",
    "gender": "Male",
    "height": 180.5,
    "allergies": ["Penicillin"],
    "married": False,
    "email": "john@ime.com"
}

patient = Patient(**patient_info)
print(patient)

Output

name='John doe' age=30 city='New York' gender='Male' height=180.5 allergies=['Penicillin'] married=False email='john@ime.com'

capitalize makes the first letter of the whole string a capital. So john doe becomes John doe, not John Doe.

Model Validator

A field validator checks one field by itself. Think of one password: is this password long enough? A model validator compares more than one field together. Think of password and confirm password: do they match?

field_validator model_validator
Checks one item by itself. Compares more than one item together.
Is this password long enough? Does password match confirm_password?

mode="after" means the check runs after the fields exist on self.

Password and confirm

from pydantic import BaseModel, field_validator, model_validator

class UserSignup(BaseModel):
    password: str
    confirm_password: str

    @field_validator("password")
    def password_length(cls, v):
        if len(v) < 8:
            raise ValueError("Password must be at least 8 characters")
        return v

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.confirm_password:
            raise ValueError("Passwords do not match")
        return self

user_info = {
    "password": "12345678",
    "confirm_password": "12345678"
}

user = UserSignup(**user_info)
print(user)

Output

password='12345678' confirm_password='12345678'

Computed Fields

A computed field is not sent by the user. It is calculated from other fields. You might have first name and last name, and you do not ask for full name. Or you have weight and height, and you need BMI. The example below uses price times quantity.

total is calculated

from pydantic import BaseModel, computed_field

class Item(BaseModel):
    price: float
    quantity: int

    @computed_field
    @property
    def total(self) -> float:
        return self.price * self.quantity

item = Item(price=10.0, quantity=3)
print(item.total)
print(item.model_dump())

Output

30.0
{'price': 10.0, 'quantity': 3, 'total': 30.0}

Pass only price and quantity. total appears on the object and in model_dump.

Nested Models

A nested model means one model is a field of another. Address could be one string like Bafal, Kathmandu, Nepal. Then it is hard to take only Kathmandu. Split it into city, state, and country.

Nested models give better organization, reuse, readability, and validation.

Address inside Patient

  1. Address city, state, country as their own model.
  2. Patient name, gender, age, plus an Address field.

Address then Patient

from pydantic import BaseModel

class Address(BaseModel):
    city: str
    state: str
    country: str

class Patient(BaseModel):
    name: str
    gender: str
    age: int
    address: Address

address_dict = {
    "city": "Kathmandu",
    "state": "Bagmati",
    "country": "Nepal"
}

address = Address(**address_dict)
print(address)

patient_info = {
    "name": "John Doe",
    "gender": "Male",
    "age": 30,
    "address": address
}

patient = Patient(**patient_info)
print(patient)

Output

city='Kathmandu' state='Bagmati' country='Nepal'
name='John Doe' gender='Male' age=30 address=Address(city='Kathmandu', state='Bagmati', country='Nepal')

Serialization

Serialization means turning a Pydantic object into a dict or JSON. FastAPI uses this a lot. Pydantic has built in methods. model_dump returns a dict. model_dump_json returns a JSON string. You can keep some fields with include, or drop some with exclude.

Dump, include, exclude

print(patient.model_dump())
print(patient.model_dump_json())
print(patient.model_dump(include={"name", "age"}))
print(patient.model_dump(exclude={"name", "age"}))

Output for the nested patient

{'name': 'John Doe', 'gender': 'Male', 'age': 30, 'address': {'city': 'Kathmandu', 'state': 'Bagmati', 'country': 'Nepal'}}
{"name":"John Doe","gender":"Male","age":30,"address":{"city":"Kathmandu","state":"Bagmati","country":"Nepal"}}
{'name': 'John Doe', 'age': 30}
{'gender': 'Male', 'address': {'city': 'Kathmandu', 'state': 'Bagmati', 'country': 'Nepal'}}

Run these lines after you build the Patient from the nested model lesson.

Day 43 takeaways

Day 43 takeaways

  • Python types are dynamic. Hints suggest. They do not force. Hand written if checks do not scale.
  • Pydantic validates and structures data. Use v2. It is used in FastAPI, YAML work, and ML pipelines.
  • Three steps: model, dict or JSON, then a valid object in your function.
  • Optional fields need a default. EmailStr and AnyUrl cover common formats.
  • Field and Annotated set gt, lt, length, defaults, and docs metadata.
  • field_validator checks one field. model_validator compares fields. computed_field calculates a value the user did not send.
  • Nest models for a clean Address. model_dump and model_dump_json serialize. include and exclude pick fields.
