Day 32

Vector Store in LangChain

Store embeddings as vectors and retrieve similar content for semantic search, RAG, and recommendations.

373

Why Do We Need a Vector Store

Think about a movie catalog recommendation system.

You already have a database with all movie details. A backend fetches data from the database and shows it in the frontend.

Now you want recommendations. How do you decide which movies match a user interest.

A first idea is keyword matching. For example, match director, actor, and genre.

But this can fail. Two movies can share many keywords and still have very different plot meaning.

To fix that, we need a way to compare meaning, not just matching keywords.

374

Keyword Matching Is Not Enough

Keyword matching only works when the same keywords imply the same meaning.

But in real recommendations, two problems show up.

  • If a key parameter matches, the recommendation may still be wrong for plot and intent.
  • If keywords differ, the system might miss a movie with a similar storyline.

So we want to compare plots. That means we need a similarity score for meaning.

375

Embeddings Turn Text Into Vectors

The solution is embedding. Embedding converts a text into a vector of numbers.

So the pipeline becomes: text goes into a neural network, then output is a vector.

Once text is numbers, comparing similarity becomes easier.

For example, you may have a vector with a fixed dimension, then you compare directions using angular distance or cosine similarity.

The closest vectors in vector space are likely to be about similar meaning.

376

Main Challenges When You Use Embeddings

Embedding helps, but it creates new work.

  • You must generate embedding vectors for many movies. With lakhs of items, this is a lot of compute.
  • You must store those vectors so you can reuse them. You cannot regenerate everything every time.
  • You must also do semantic search fast. Comparing a query against every vector is too slow.

This is why you need a different kind of storage and retrieval system.

377

What Is a Vector Store

A vector store is a system to store and retrieve data as numerical vectors.

It stores vectors plus metadata. It can keep data in memory or on disk.

Key features in practice are these:

  • Store vectors with metadata.
  • Perform similarity search for a query vector.
  • Index the vectors so search is fast.
  • Support CRUD operations like add, update, and delete.

Vector stores are used for semantic search, RAG, recommendation systems, and image or multimedia search.

378

Indexing Makes Semantic Search Fast

If you have 10 lakh vectors, and you compare a query against every one, it is slow.

So vector stores use indexing. One idea is clustering.

Clustering and centroids for faster search

  1. Lots of vectors For example 10 lakh vectors.
  2. Cluster them Group similar vectors together.
  3. Compute centroids Represent each cluster by one vector.
  4. Compare fewer vectors Find the closest cluster first.
  5. Search inside that cluster Now compare against fewer candidates.

In your notes, the idea is: do one comparison against centroids, then focus on one cluster. That reduces the total work from millions of comparisons down to far fewer.

379

CRUD Operations and Metadata

Vector stores are not only for searching. They also support CRUD operations.

So you can add new vectors, update existing vectors, and delete vectors that are no longer needed.

Each vector is tied to metadata. That metadata might include the original document id, source, title, or any fields you want to return with search results.

380

Vector Store versus Vector Database

Vector store and vector database are very close ideas.

A good way to remember the difference is feature depth.

Here is the comparison at a glance.

Category What it focuses on Example
Vector store Lightweight library for storage and retrieval. Often fewer database style features. FAISS.
Vector database More complete database features such as distributed architecture, backup, concurrency, and authentication. Pinecone.

In short: vector stores help you do the core job fast. Vector databases add heavier backend features for production scale.

Chroma Example in LangChain

LangChain includes wrappers for many vector stores. They share the same method shapes for adding documents and running similarity search.

Here is a minimal example using Chroma. It works with OpenAI embeddings if you have an API key, otherwise it uses deterministic offline embeddings so the script can run.

Input code

"""
Minimal working example of using Chroma (via LangChain).

Run:
  python3 chroma.py

Notes:
1) If you have `OPENAI_API_KEY` set and `langchain-openai` is installed, this uses `OpenAIEmbeddings`.
2) Otherwise it falls back to deterministic offline embeddings so the script can run without API calls.
"""
from __future__ import annotations
import hashlib
import os
from dataclasses import dataclass
from typing import List

import numpy as np

try:
    # Newer import path in many setups.
    from langchain_community.vectorstores import Chroma  # type: ignore
except Exception:  # pragma: no cover
    # Older LangChain versions exposed vectorstores here.
    from langchain.vectorstores import Chroma  # type: ignore

try:
    from langchain_core.documents import Document
except Exception:  # pragma: no cover
    from langchain.schema import Document  # type: ignore

try:
    from langchain_core.embeddings import Embeddings
except Exception:  # pragma: no cover
    from langchain.embeddings.base import Embeddings  # type: ignore

try:
    from langchain_openai import OpenAIEmbeddings  # type: ignore
except Exception:  # pragma: no cover
    OpenAIEmbeddings = None  # type: ignore


@dataclass
class SimpleEmbeddings(Embeddings):
    """
    Offline fallback embeddings for examples.

    Produces deterministic vectors from text hashes.
    """

    dim: int = 384

    def _embed_text(self, text: str) -> List[float]:
        digest = hashlib.sha256(text.encode("utf-8")).digest()
        needed = self.dim
        buf = (digest * ((needed + len(digest) - 1) // len(digest)))[:needed]
        arr = np.frombuffer(buf, dtype=np.uint8).astype(np.float32) / 255.0
        return arr.tolist()

    def embed_documents(self, texts: List[str]) -> List[List[float]]:
        return [self._embed_text(t) for t in texts]

    def embed_query(self, text: str) -> List[float]:
        return self._embed_text(text)


def build_embedding():
    api_key = os.getenv("OPENAI_API_KEY", "").strip()
    if OpenAIEmbeddings is not None and api_key:
        return OpenAIEmbeddings()
    return SimpleEmbeddings()


def main() -> None:
    persist_directory = "chroma_db"
    collection_name = "sample"

    embedding = build_embedding()

    docs = [
        Document(page_content="Hello, how are you?", metadata={"source": "doc1.txt"}),
        Document(page_content="This is a test document.", metadata={"source": "doc2.txt"}),
        Document(page_content="This is a test document 3.", metadata={"source": "doc3.txt"}),
        Document(page_content="This is a test document 4.", metadata={"source": "doc4.txt"}),
    ]
    ids = ["doc1", "doc2", "doc3", "doc4"]

    # Create an empty collection, then add docs with explicit IDs.
    vector_store = Chroma(
        collection_name=collection_name,
        embedding_function=embedding,
        persist_directory=persist_directory,
    )
    vector_store.add_documents(docs, ids=ids)
    vector_store.persist()

    stored = vector_store.get(include=["metadatas", "documents"])
    print("Stored docs:", len(stored.get("documents", [])))

    # Similarity search (score + docs).
    query = "what is the question"
    results = vector_store.similarity_search_with_score(query=query, k=2)
    print("Similarity results (Document, score):")
    for doc, score in results:
        print("-", doc.metadata.get("source"), "score=", score)

    # Update an existing document (add it first with id="doc5").
    doc5 = Document(
        page_content="This is an updated test document 5.",
        metadata={"source": "doc5.txt"},
    )
    vector_store.add_documents([doc5], ids=["doc5"])
    vector_store.update_documents([doc5], ids=["doc5"])
    vector_store.persist()

    # Delete the document.
    vector_store.delete(ids=["doc5"])
    vector_store.persist()


if __name__ == "__main__":
    main()

What you get

Stored docs: 4
Similarity results (Document, score):
- <source> score= ...
- <source> score= ...

The exact similarity scores can change depending on embeddings. The stored docs count is 4 because the code starts by inserting 4 documents.

After this, you can use the vector store as the retrieval source for RAG, semantic search, and recommendations.

Day 32 takeaways

Day 32 takeaways

  • Keyword matching can fail because it compares surface features, not plot meaning.
  • Embeddings convert text into vectors, then similarity is computed in vector space.
  • Vector stores solve the embedding storage and fast retrieval problem.
  • Indexing helps semantic search stay fast by comparing fewer vectors using clustering ideas.
  • Vector stores and vector databases are similar, but databases include heavier production features.
