Persistence in LangGraph

Save and restore workflow state over time. Checkpoints, threads, fault tolerance, and a joke graph that keeps its saved state.

What Is Persistence

Persistence is the ability to save and restore the state of a workflow over time. Without it, a run finishes and the values you put in at START are gone. With it, those values stay, so you can load them later.

717

Recap: State

When we create a graph in LangGraph, we make the state first. State is the input data the workflow needs. It is a dictionary. For a chatbot, that input can be messages. Each node can read the state. Each node can also change the state. Graph and state are the core ideas of LangGraph.

718

Default Run Versus Save

Watch a normal run. We give input. START runs. Node 1 runs, then node 2, and so on. The state changes at each node. We get a final state. Then the data we put in at START is erased. Persistence changes that behaviour. We can save the values stored in the state. Persistence does not keep only the final value. It also keeps the value after each node. The table below puts those two paths side by side.

Without persistence With persistence
Input goes in. Nodes run. You get a final state. The same run also writes the state after each node.
When the run ends, the start data is gone. You can load the saved values later from a store or a database.
719

Fault Tolerance

Suppose we are running a workflow and node 1 stops for any reason. Because we save the state at each node, we can start again from the node that crashed. We do not restart the whole graph. That is the biggest feature here. It is called fault tolerance. That feature comes from persistence. Persistence values can live in a database.

A chatbot uses the same idea. You have two options. Start a fresh conversation. Or continue the previous conversation. Persistence is what makes the second option possible.

Checkpointer

A checkpointer is the persistence concept that splits a workflow into checkpoints. The graph runs. The checkpointer saves the state. A super step can be one checkpoint. START is one checkpoint. Node 1 is another. From node 1, node 2, node 3, and node 4 run in parallel. Their results combine at END. Those three nodes share one checkpoint. END is the last checkpoint. A List That Grows

722

Threads

Run the same workflow two times. The first run gets input 2 and that output is saved. The second run gets input 4 and a different output. Those are two threads. If we need to resume the first run, the database loads that particular workflow. The answer comes from the thread.

When we add persistence we assign a unique thread id. Each workflow execution has its own thread id. If we want the values of execution 5, we ask the database for the state of thread 5.

A chatbot uses this too. As soon as a user starts a fresh conversation, the app gives that conversation a thread id and stores the data. Later we resume with that same thread id.

723

Joke Workflow

We write a workflow that uses persistence and a thread. START goes to gen_joke. Then gen_explanation. Then END. State holds topic, joke, and explanation. The diagram below is that line.

State and nodes

from typing import TypedDict
from dotenv import load_dotenv
from langchain_openrouter import ChatOpenRouter
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()

llm = ChatOpenRouter(
    model="openai/gpt-4o-mini",
    temperature=0
)

class JokeState(TypedDict):
    topic: str
    joke: str
    explanation: str

def gen_joke(state: JokeState):
    prompt = f"Generate a joke about the topic: {state['topic']}"
    response = llm.invoke(prompt)
    return {
        "joke": response.content
    }

def gen_explanation(state: JokeState):
    prompt = f"Generate an explanation for this joke: {state['joke']}"
    response = llm.invoke(prompt)
    return {
        "explanation": response.content
    }

gen_joke writes joke. gen_explanation reads that joke and writes explanation.

724

Compile, Invoke, Get State

We compile with InMemorySaver as the checkpointer. config sets thread_id to 123. invoke sends topic programming. After the run, get_state(config) loads the saved values for that thread. Print result, then print state.values.

Checkpointer, thread, run

graph = StateGraph(JokeState)

graph.add_node("gen_joke", gen_joke)
graph.add_node("gen_explanation", gen_explanation)

graph.add_edge(START, "gen_joke")
graph.add_edge("gen_joke", "gen_explanation")
graph.add_edge("gen_explanation", END)

checkpoint = InMemorySaver()

workflow = graph.compile(
    checkpointer=checkpoint
)

config = {
    "configurable": {
        "thread_id": "123"
    }
}

result = workflow.invoke(
    {
        "topic": "programming"
    },
    config=config
)

print("RESULT:")
print(result)

state = workflow.get_state(config)

print("\nSAVED STATE:")
print(state.values)

The joke text and the explanation come from the model. We do not paste a fake joke here. Run the cell to see yours. InMemorySaver keeps this thread in process memory. A database checkpointer would keep it after the program stops.

725

Four Benefits

Persistence gives four benefits. The cards below are that set. We open the last two next.

Short term memory

To resume a chatbot we need the past conversation. We only have it if we store it, often in a database.

Fault tolerance

If a node stops in the middle, we restart from that node. We do not restart the whole workflow.

Human in the loop

The graph can wait for a person. Persistence holds the state until that person answers.

Time travel

Replay an earlier checkpoint. Go back and run again. This helps with debugging.

726

Human in the Loop

Imagine a workflow that takes a topic, generates a LinkedIn post, then posts it through the LinkedIn API. Before it posts, we want it to ask us for permission.

The person might answer at once, or after two days. The workflow cannot sit running that whole time. LangGraph holds the workflow until the human gives input. As soon as that input arrives, we need persistence to resume. This is similar to fault tolerance, but here we pause on purpose.

Wait, then resume

  1. Generate Write the LinkedIn post from the topic.
  2. Ask Hold the saved state. Wait for yes or no.
  3. Post Resume and call the API only after permission.
727

Time Travel

In time travel we replay the execution of the workflow. We go back to a previous checkpoint and run again the way we want. We can do debugging with it. The saved checkpoints are the history we step through.

Day 55 takeaways

Day 55 takeaways

  • Persistence means save and restore workflow state over time.
  • A graph is nodes and edges. State is the dictionary the nodes read and write.
  • Without persistence, start data is erased after the run. With it, each node can leave a checkpoint.
  • Fault tolerance lets us resume from a crashed node instead of restarting the whole graph.
  • A checkpointer writes those checkpoints. A thread id keeps one execution apart from another.
  • The four benefits are short term memory, fault tolerance, human in the loop, and time travel.
