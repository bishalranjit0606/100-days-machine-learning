Multiple Failure Points

The most important reason is this. In an LLM app there can be multiple failure points. In a RAG chatbot the retriever fetches the docs, then the generator writes the answer. Either step can fail. So we need one evals pipeline for the retriever, and one for the generator. The flow below is those two points.

RAG chatbot

  1. Retriever It can fetch the wrong docs. One evals pipeline here.
  2. Generator It can write a wrong or ungrounded answer. One evals pipeline here.

Latency Needs Its Own Check

A retriever can fetch good docs. A generator can write a grounded answer. The app can still fail if it takes a long time to reply. Latency must come under a certain threshold. That is a different evals pipeline from retrieval or generation. The flow below is that extra check.

Safety

Safety means the RAG chatbot should not accept prompt injection, and it should not use bad words. A quality score can look fine while the app is still unsafe. That is why safety is its own evals pipeline. The cards below are those two checks.

Operations

Operations asks, is it fast, easy, cheap, and reliable? Token cost sits here, because cheap is part of operations. A correct and safe answer can still fail this check if it is slow or expensive. The cards below are those four.

Day 73 takeaways

Day 73 takeaways

  • One evals pipeline is not enough. An LLM app has multiple failure points, so we cannot see the break from the last answer alone.
  • A RAG chatbot needs a retriever evals pipeline and a generator evals pipeline. Retrieval finds similar docs. Generation must be correct in context and grounded, not extra lines like it is a great course.
  • Two component evals still do not finish the job. We also eval the workflow and the entire application, including latency under a threshold.
  • Risk comes in three categories. Application quality is correct, relevant, and complete. Safety is no prompt injection and no bad words. Operations is fast, easy, cheap, and reliable, including token cost.
