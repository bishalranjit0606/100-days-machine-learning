Three Problems in Traditional RAG

There are three main problems in traditional RAG. It retrieves even when retrieval is unnecessary. The LLM blindly trusts the retrieved context. And RAG does not verify its own answer. The cards below are those three.

Indiscriminate retrieval

It retrieves for every query, even when the LLM already knows.

Blind trust

It uses the retrieved docs no matter what semantic search returned.

No verify

Once the answer is generated, nothing checks it.

933

Retrieval When We Do Not Need It

The first main problem is this. RAG retrieves even when retrieval is unnecessary. Like this. We make a RAG chatbot to reply. A child asks how many seconds are in a minute. The issue is RAG will retrieve all the details from the vector db. There are many docs that we retrieve. The LLM knows the answer, but RAG still provides other context. That extra context is not good. It is unnecessary. There are certain scenarios where we do not need to retrieve, but in traditional RAG we retrieve no matter what the query is. This is called indiscriminate retrieval, and this is very bad. The table below is that miss.

The question What traditional RAG does
How many seconds are in a minute? It still pulls many docs from the vector db. Extra context the LLM does not need.
934

The LLM Blindly Trusts Retrieval

The second problem is this. The LLM blindly trusts the retrieved context. As we know, the docs are retrieved with semantic search, and RAG usually tries to use those retrieved docs no matter what. Last day, CRAG put a check before generation. Self RAG also refuses to trust the docs blindly. It judges them itself.

935

RAG Does Not Verify Its Answer

The third problem is this. RAG does not verify its own answer. Ideally, once the answer is generated, it needs to be checked. Traditional RAG stops at generation. Self RAG keeps going. It asks if the answer came from the docs, and if it actually answers the user.

936

Self Reflective RAG

Self RAG means self reflective RAG. The LLM actively judges its own retrieval, evidence, and answer, instead of blindly trusting retrieved documentation. Self RAG judges its own action by itself. It is self conscious. It is aware of its own action and decision. That is the main strength. The table below is that shift.

Traditional RAG Self RAG
Retrieve, then generate. Trust the docs. Judge retrieval, evidence, and the answer first.

Four Questions

Self RAG tries to answer four most important questions. Is retrieval even required? Are the retrieved documents relevant? Does the answer come from the documentation itself, or did the LLM generate it by hallucinating? Does the response actually answer the user query? The cards below are those four.

Need retrieve?

Is retrieval required for this query, or not?

Docs relevant?

Is each retrieved document relevant?

From the docs?

Did the answer come from the docs, or from hallucination?

Answers the user?

Does the response actually answer the query?

Decide If Retrieval Is Required

Step 1. START, then decide if we need retrieval or not. We use an LLM here to decide. If retrieval is required, we retrieve from the vector store. If not, we answer through parametric knowledge. That is the knowledge already inside the model. Like this. Retrieval is needed if the user asks how many paid leave days employees get per year. What is a paid leave? Now we do not need retrieval. We will answer through a parametric reply. The picture below is that first branch.

Keep Only Relevant Docs

Step 2. Once we retrieve, we check if each retrieved document is relevant. We only keep the ones that are relevant. We discard the rest. If there is one document that is relevant, we use it for the next step. We generate the answer based on the relevant documentation. The steps below are that filter.

After retrieve

  1. All docs The vector store sent some chunks.
  2. Ask per doc Is this documentation relevant to the query?
  3. Keep relevant Discard the rest. Generate from the ones we kept.

If None Are Relevant

If none of the documentation is relevant, we return no answer found. We can also say we do not have the details. What we can do, if none is relevant, is add a web search tool. For that we need to add query rewrite, then search. We do not invent that web search node here. The table below is that choice.

Simple stop Optional extra
Return no answer found. We do not have the details. Rewrite the query, then search the web.

Generate Then Judge the Evidence

Once the answer is generated, we check if the answer is correct, or if it is giving an answer from that documentation. We check if the generated answer used the context we gave. That is so the AI is not hallucinating. This is an LLM that is judging, based on the query and the context, whether the LLM is generating a correct answer. Like this. We have 3 docs as context, but the LLM only used 2. We still need to see if what it wrote is supported. The picture below is generate, then judge.

942

Fully Supported, Partial, No Support

There are conditions like fully supported, partial supported, and incorrect, that is no support. Fully supported means the answer comes from the documentation. We accept that. Partial supported means it takes a partial answer from the documentation, and the LLM adds its own answer on top. No support means the LLM is not taking anything from the documentation and is generating the answer on its own. The model is generating its own answer. That is a proper hallucination. Partial supported and no support go into a loop. The cards below are those three.

Fully supported

The answer comes from the docs. We accept it.

Partial supported

Part from the docs. The LLM adds its own words.

No support

Nothing from the docs. That is hallucination.

943

Revise Answer Loop

We use a revise answer node in a loop. We check again and again to fix the partial answer and the no support answer. If the judge says okay, we go on. If it is false, we go back to retrieve the docs, and the loop starts. We need to add a max tries condition to break the loop, so it can stop an infinite try. After a certain number of loops we end the loop. The picture below is that loop.

944

Is the Answer Useful

Now the last step. Evaluate if the generated answer is useful or not, from the query. Why use this when we already checked the answer in the previous node and only got the right answer? Because although the answer is totally right, and it is not hallucinating, it can still miss the main point. Like it only uses doc 2 and doc 3, but ignores doc 1, which has the main answer. We send it to an LLM evaluation. That LLM evaluates if the answer is useful or not. The table below is that sick leave case.

What we had What the LLM said
Question. What is the policy for sick leave? You need to write a letter for approval and apply through the portal.
Doc 1. You can take 10 sick leave per year. This main fact is missing.
Doc 2. You need to write an email for leave approval. Doc 3. You can apply leave through the portal. The reply used these two. It is not hallucinating. It is still not the useful answer.
945

Rewrite and Try Again

If the answer is useful, we end the workflow. If it is not useful, we need to rewrite the query. That means optimize it, using an LLM, and go back to retrieve. The loop starts again. We retrieve the docs, check if they are relevant, and so on. Here as well it is a proper loop. Add a max tries condition to break the loop so it can stop an infinite try. If we do not get the answer after that, we return no answer is found. The steps below are that last loop.

Useful or not

  1. Useful End the workflow. The user gets the answer.
  2. Not useful Rewrite the query with an LLM. Retrieve again.
  3. Max tries Stop the infinite try. Return no answer found.

Day 70 takeaways

Day 70 takeaways

  • Traditional RAG has three problems. Indiscriminate retrieval. Blind trust. No check on the generated answer.
  • Self RAG means self reflective RAG. The LLM judges its own retrieval, evidence, and answer.
  • First decide if retrieval is required. Paid leave counts need the store. What is paid leave can use parametric knowledge.
  • Keep only relevant docs. If none are relevant, return no answer found, or rewrite and search the web.
  • Accept fully supported answers. Loop on partial support and no support. Use max tries so the loop can stop.
  • An answer can be grounded and still not useful, like the sick leave reply that skipped the 10 days. If it is not useful, rewrite the query and retrieve again.
