Subgraphs in LangGraph

Until now each task was a node. Today a node can be a whole graph. We embed that graph, run it, and keep the parent simple.

What Is a Subgraph

Until now we have made a graph in LangGraph. That graph is made of nodes. Each task is a node. What if we replace a node with a graph? The node becomes a bigger graph that still sits in one place. A subgraph in LangGraph usually means a graph that is embedded and executed as a node inside another graph. The picture below is that idea.

850

Apps Get Complex

Why use a subgraph? First, when we make a Gen AI system it can look like user, then LLM, then output. As we go on, it gets more complex. Retry. Memory. Guard rails. HITL. A big Gen AI app can have a lot of things. One flat graph gets hard to see. The steps below are that growth.

From simple to many jobs

  1. User to LLM Ask, get an answer. One line of work.
  2. More pieces Retry, memory, guard rails, and HITL join the same app.
  3. Split the graph Put a cluster of jobs in a subgraph so the parent stays small.
851

Teams in a Software Company

Suppose we are making software like a PM in a software company. There is a front end team and a back end team. They combine and send work to a test team. Then it goes to a devops team. That can feel like one huge thing. We make it simple by dividing the work. One node is front end. One node is back end. We convert this big architecture into a small multi agent architecture. The steps below are those teams.

Divide the work

  1. Front end One team, one node, or one subgraph.
  2. Back end Another team. Combine with front end when both are ready.
  3. Test The combined work goes to the test team.
  4. Devops Tested work goes to devops.
852

Modularity, Reuse, Maintain

Why use a subgraph in the code? Three reasons sit here. Modularity means we break the code base into functions, like small graphs. Reusability means we can call the same subgraph from more than one parent. Maintainability means a change in translate does not force a rewrite of generate. The cards below are those three.

Modularity

Break the code base into functions. Each subgraph is one job.

Reusability

Compile once. Use that graph as a node in more than one parent.

Maintainability

Fix one subgraph without touching every other node.

853

LangGraph Benefits

LangGraph also gives three subgraph benefits. Failure isolation: if a subgraph is down, the other nodes do not all go down with it. State separation: each graph has state. If every component shared the same keys, those keys could clash. A subgraph can keep its own state so the parent and the child do not mismatch. Observability: each subgraph can be observed separately in LangGraph. The cards below are those three.

Failure isolation

A down subgraph does not take every other node with it.

State separation

Each graph can hold its own state. Keys do not clash.

Observability

Watch one subgraph on its own in LangGraph traces.

Two Ways to Add a Subgraph

How do we implement a subgraph in LangGraph? There are two ways. First, we invoke the graph inside a node. The parent graph calls the subgraph from that node. Second, we add the compiled graph as a subgraph instead of a function node. The first way has its own state. The second way shares the same state. The table below is that split.

Invoke inside a node Add the graph as a node
A parent node calls subgraph.invoke. parent_builder.add_node takes the compiled subgraph.
The subgraph has its own state. Parent and subgraph share the same state.
We map parent keys into subgraph keys, then map back. The same field names flow through both graphs.
855

English Then Nepali

Here is the use case. The user asks. An LLM generates an answer in English. Another LLM translates that answer into Nepali. Then we output. The graph is START, generate, translate, output. Translate is the subgraph. The steps below are that path.

Generate, then translate

  1. START The parent gets user_input.
  2. Generate Answer the question in English. This stays in the parent.
  3. Translate This node is the subgraph. English becomes Nepali.
  4. END The parent holds the final Nepali answer.
856

Own State, Then Map

We start with the first way. The subgraph has SubState: english_text and nepali_text. The parent has ParentState: user_input, english_answer, and final_answer. Names do not match, so the parent node maps them. english_answer becomes english_text. nepali_text becomes final_answer. The picture below is that map. We do not invent the texts. Run the graph to see yours.

Two state types

class SubState(TypedDict):
    english_text: str
    nepali_text: str


class ParentState(TypedDict):
    user_input: str
    english_answer: str
    final_answer: str

The subgraph never sees user_input. The parent never stores english_text.

857

Invoke the Subgraph Inside a Node

translate_to_nepali reads english_text, asks the model to return only the translation, and writes nepali_text. We compile that as subgraph. In the parent, call_translation_subgraph builds the subgraph input from english_answer, calls subgraph.invoke, then returns final_answer from nepali_text. That is invoke inside a node. The blocks below are those pieces.

Subgraph node and compile

def translate_to_nepali(state: SubState):
    response = llm.invoke([
        SystemMessage(
            content="Translate the following English text into "
                    "natural Nepali. Return only the translation."
        ),
        HumanMessage(content=state["english_text"])
    ])

    return {"nepali_text": response.content}


sub_builder = StateGraph(SubState)
sub_builder.add_node("translate", translate_to_nepali)
sub_builder.add_edge(START, "translate")
sub_builder.add_edge("translate", END)
subgraph = sub_builder.compile()

Map, invoke, map back

def call_translation_subgraph(state: ParentState):
    subgraph_result = subgraph.invoke({
        "english_text": state["english_answer"]
    })
    return {
        "final_answer": subgraph_result["nepali_text"]
    }

This function is a normal parent node. Inside it we call the compiled subgraph.

Build the Parent, Way 1

generate_answer reads user_input and writes english_answer. The parent adds generate, then translate, which is call_translation_subgraph. START to generate, generate to translate, translate to END. We invoke with user_input set to What is artificial intelligence? We print english_answer and final_answer. We do not invent those two strings here. Run the file to see what your model writes.

Imports and model

from dotenv import load_dotenv
from typing_extensions import TypedDict

from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openrouter import ChatOpenRouter
from langgraph.graph import START, END, StateGraph

load_dotenv()

llm = ChatOpenRouter(
    model="openrouter/free",
    temperature=0,
)

Parent graph and run

def generate_answer(state: ParentState):
    response = llm.invoke([
        SystemMessage(
            content="Answer the user's question in English."
        ),
        HumanMessage(content=state["user_input"])
    ])
    return {"english_answer": response.content}


parent_builder = StateGraph(ParentState)
parent_builder.add_node("generate", generate_answer)
parent_builder.add_node("translate", call_translation_subgraph)
parent_builder.add_edge(START, "generate")
parent_builder.add_edge("generate", "translate")
parent_builder.add_edge("translate", END)
graph = parent_builder.compile()

result = graph.invoke({
    "user_input": "What is artificial intelligence?"
})
print("English Answer:", result["english_answer"])
print("Nepali Answer:", result["final_answer"])

translate in the parent is a function that invokes the subgraph. It is not add_node with the compiled graph yet.

859

Add the Graph as a Node

The second way shares one GraphState: user_input, english_answer, and final_answer. translate_to_nepali reads english_answer and writes final_answer. We compile that subgraph on GraphState. The parent adds generate as a function, then adds the compiled subgraph with parent_builder.add_node("translate", subgraph). No mapping function. Same keys. Same invoke input as way 1. The picture below is parent plus nested translate. The block below is that add_node call.

Shared state and add_node

class GraphState(TypedDict):
    user_input: str
    english_answer: str
    final_answer: str


def translate_to_nepali(state: GraphState):
    response = llm.invoke([
        SystemMessage(
            content="Translate the following English text "
                    "into natural Nepali. Return only the translation."
        ),
        HumanMessage(content=state["english_answer"])
    ])
    return {"final_answer": response.content}


sub_builder = StateGraph(GraphState)
sub_builder.add_node("translate_to_nepali", translate_to_nepali)
sub_builder.add_edge(START, "translate_to_nepali")
sub_builder.add_edge("translate_to_nepali", END)
subgraph = sub_builder.compile()


parent_builder = StateGraph(GraphState)
parent_builder.add_node("generate", generate_answer)
parent_builder.add_node("translate", subgraph)
parent_builder.add_edge(START, "generate")
parent_builder.add_edge("generate", "translate")
parent_builder.add_edge("translate", END)
graph = parent_builder.compile()

generate_answer is the same idea as way 1. It still writes english_answer from user_input.

Day 65 takeaways

Day 65 takeaways

  • A subgraph is a graph embedded and run as a node inside another graph.
  • We use it when an app grows: retry, memory, guard rails, HITL, many teams.
  • Modularity, reuse, and maintainability keep the parent small.
  • LangGraph also gives failure isolation, state separation, and separate traces.
  • Way 1 invokes the subgraph inside a node and maps its own state.
  • Way 2 adds the compiled subgraph with add_node and shares GraphState.
  • Our path is generate English, then a translate subgraph into Nepali.
