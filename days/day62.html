MCP in LangGraph

MCP is a standard way to connect tools. The chatbot is the client. An MCP server holds the tools. We stay on the client and run it with async.

808

MCP Is a Better Way to Add Tools

MCP is the improved version of tools. We added tools in the chatbot to make it more capable. There is a problem, and MCP solves that problem. It is a better way to add tools to an LLM application. It is a standardized way of connecting a tool.

809

The GitHub Problem

In our chatbot we added three tools. Search with DuckDuckGo, latest share price, and calculator. DuckDuckGo is a library based tool. The other two are user defined tools. Now we want the chatbot to connect with GitHub, read the code, and give an answer. GitHub did not give us that tool. So we would write our own code. Tokens. Headers. And more. For only a pull request we would make a different tool. For a commit another tool. Same for push, pull, and the rest. That process can break at any time.

One GitHub app, many tools

  1. PR tool Write tokens and headers for pull requests.
  2. Commit tool Another tool for commits.
  3. Push and pull Still more tools. Any one of them can break.
810

APIs Change and More Apps Arrive

Suppose we used a GitHub API. A get URL might change, like from /git to /github-pull. After that change, our code will not work. As a coder we have to update the code. We go to the GitHub website, see the version is updated, and we need to update every time. If it is only 1 tool, it might be okay. For 10 API requests of GitHub we need to change all of them. Then the company says connect Slack, Gmail, and more. That takes too much time and effort. This is the biggest problem of the tool.

811

m times n Versus m plus n

Without MCP it would be m times n. With MCP it would be m plus n. Each app does not rewrite every tool. The table below is that idea.

Without MCP With MCP
m times n. Every client writes every GitHub, Slack, and Gmail call. m plus n. Each client plus each server. The server owns the tools.
An API change means we edit many tools in our app. The server updates. Our client config can stay the same.

814

We Build the Client

For MCP we need to create two things. An MCP server and an MCP client. We will work with the MCP client. We cannot make the MCP server from LangGraph. We need FastMCP for a server. In this chatbot we connect to servers that already exist. Time, weather, and SportScore.

815

MCP Client Needs Async

Our code so far is in synchronous mode. The MCP client works only in async mode. So we need to convert it to async and await. Why do we use async code. In sync code, suppose we say find the weather of Kathmandu and the score of a cricket match. First it will find the weather, then only find the score. With async it will be much faster. MCP client only works with async. The picture below is wait in a line versus overlap.

816

MultiServerMCPClient

The working import is langchain_mcp_adapters.client. MultiServerMCPClient. We start each MCP server with this project Python, so it runs in the same virtual env. Time uses mcp_server_time with local timezone Asia/Kathmandu. Weather uses mcp_weather_server. SportScore uses npx sportscore-mcp. transport is stdio. tool_name_prefix True so names like time_get_current_time do not clash.

_mcp_client

from langchain_mcp_adapters.client import MultiServerMCPClient

def _mcp_client():
    python = sys.executable
    return MultiServerMCPClient(
        {
            "time": {
                "command": python,
                "args": ["-m", "mcp_server_time", "--local-timezone=Asia/Kathmandu"],
                "transport": "stdio",
            },
            "weather": {
                "command": python,
                "args": ["-m", "mcp_weather_server"],
                "transport": "stdio",
            },
            "sportscore": {
                "command": shutil.which("npx") or "npx",
                "args": ["-y", "sportscore-mcp"],
                "transport": "stdio",
            },
        },
        tool_name_prefix=True,
    )

We did not write these three servers in LangGraph. We only start them and ask for their tools.

818

Load MCP Tools and Compile

_open_chatbot is async. It makes the MCP client, awaits get_tools, then builds one tools list. Local tools plus MCP tools. It binds that list. The checkpointer is AsyncSqliteSaver on aiosqlite. The graph is still START, chat_node, tools_condition, and tools back to chat_node.

_open_chatbot

async def _open_chatbot():
    global llm_with_tools, tools, _mcp

    _mcp = _mcp_client()
    mcp_tools = await _mcp.get_tools()
    tools = [calculator, get_stock_price, duckduckgo_search, *mcp_tools]
    llm_with_tools = llm.bind_tools(tools)

    conn = await aiosqlite.connect(db_path)
    saver = AsyncSqliteSaver(conn)
    await saver.setup()

    graph = StateGraph(ChatState)
    graph.add_node("chat_node", chat_node)
    graph.add_node("tools", ToolNode(tools, handle_tool_errors=True))
    graph.add_edge(START, "chat_node")
    graph.add_conditional_edges("chat_node", tools_condition)
    graph.add_edge("tools", "chat_node")
    return graph.compile(checkpointer=saver), saver

Import AsyncSqliteSaver from langgraph.checkpoint.sqlite.aio. The db path helper is the same as Day 61.

819

Streamlit Stays Synchronous

Streamlit stays synchronous. We start one asyncio loop on a daemon thread. _run sends a coroutine to that loop and waits. _iter_async turns astream into a normal for loop, so the page can still stream chunks. _Chatbot.stream and get_state wrap the compiled graph. get_all_threads runs the same SQL as Day 61, but with await on the async connection.

Loop bridge

_loop = asyncio.new_event_loop()
_loop_ready = threading.Event()

def _run_loop():
    asyncio.set_event_loop(_loop)
    _loop.call_soon(_loop_ready.set)
    _loop.run_forever()

threading.Thread(target=_run_loop, name="langgraph-async", daemon=True).start()
_loop_ready.wait()

def _run(coro):
    return asyncio.run_coroutine_threadsafe(coro, _loop).result()

_compiled, checkpointer = _run(_open_chatbot())

class _Chatbot:
    def stream(self, inputs, config, stream_mode="messages"):
        return _iter_async(
            lambda: _compiled.astream(inputs, config, stream_mode=stream_mode)
        )

    def get_state(self, config):
        return _run(_compiled.aget_state(config))

chatbot = _Chatbot()

_iter_async uses a queue. The loop thread puts items. The Streamlit thread yields them.

Day 62 takeaways

Day 62 takeaways

  • MCP is a standard way to connect tools. It is the improved version of writing every tool yourself.
  • GitHub, Slack, and Gmail would need many custom tools. Tokens, headers, and API changes break them.
  • Without MCP the work is m times n. With MCP it is m plus n.
  • The chatbot is the client. The MCP server holds the tools. Heavy lifting stays on the server.
  • LangGraph does not build the server. Use FastMCP for a server. We use MultiServerMCPClient.
  • MCP client is async only. We await get_tools, ainvoke, astream, and aget_state.
  • This app starts time, weather, and SportScore over stdio, then binds those tools with the local three.
  • Streamlit stays sync. A background loop runs the async graph.
