Day 25

Structured Output in LangChain

Turn free text LLM replies into JSON shaped data with TypedDict, Pydantic, and JSON Schema.

379

Why Structured Output Matters

The biggest advantage of an LLM is that it can communicate in natural language.

Real apps also need to connect that LLM to an API, a database, or other tools.

Today we learn how to shape the LLM output so other systems can use it safely.

380

Unstructured vs Structured

Unstructured output: you give a prompt, the LLM answers in free text. That text is hard to plug into code without parsing by hand.

Structured output: the LLM returns formatted data, often like JSON, with known fields.

Structure is a powerful technique. Without it, you mostly get text. With it, you can hand fields to tools and databases.

381

Use Cases

Common places structured output helps:

  1. Data extraction. On a job portal, people upload resumes. You send the resume text to the LLM and get JSON fields back, ready to store.
  2. API building. Think of product reviews on a shop like Amazon. The LLM returns key details in JSON: product focus, good or bad tone, and more.
  3. Agents with tools. A chatbot only answers. An agent acts. When an agent calls tools, it needs structured arguments, not only chat text.
382

Two Paths to Structure

There are two kinds of LLMs for this topic:

  1. Models that can generate structured output on their own.
  2. Models that cannot do that cleanly.

For models that support it, use with_structured_output.

For models that cannot, use an output parser after the free text reply.

This day focuses on with_structured_output.

383

Three Data Formats

When you call with_structured_output, you usually pick one of three shapes:

  1. TypedDict for type hints and a simple dict result.
  2. Pydantic for real validation and safer objects.
  3. JSON Schema when many languages must share one schema.

You wrap the model once, then invoke as usual:

structured_model = model.with_structured_output(Review)
result = structured_model.invoke("This is a very good mobile. I give it 5 stars.")
384

TypedDict Basics

A plain dict can hide type mistakes. One developer might store age as a number. Another might store it as a string.

TypedDict tells tools and teammates the expected keys and types:

from typing import TypedDict

class Person(TypedDict):
    name: str
    age: int

new_person: Person = {
    "name": "bishal",
    "age": 35,
}

Your editor can warn when name is not a string or age is not an int.

Important limit: TypedDict is mainly for data representation and type hints. It does not validate at run time. Bad values can still get through.

385

Review Extraction with TypedDict

Send a phone review to the LLM and ask for a dict with summary and sentiment.

from langchain_groq import ChatGroq
from dotenv import load_dotenv
from typing import TypedDict

load_dotenv()

model = ChatGroq(model="llama-3.3-70b-versatile")

class Review(TypedDict):
    summary: str
    sentiment: str

structured_model = model.with_structured_output(Review)

result = structured_model.invoke(
    "This is a very good mobile. I give it 5 stars."
)

print(result)
print(type(result))
print(result["summary"])

You get a dictionary back.

You did not spell out “write a summary and sentiment” in the user prompt. LangChain still guides the model with a system style schema behind the scenes based on your TypedDict fields.

386

Annotated Guidance

Sometimes the LLM still gets confused. Use Annotated to add a short hint for each field.

from typing import TypedDict, Annotated

class Review(TypedDict):
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[
        str,
        "Sentiment: negative, positive, or neutral",
    ]

Those hints travel with the schema so the model knows what each field means.

387

Optional and Literal

Richer reviews need more fields. Three helpers matter:

  • TypedDict: tell humans and tools which keys exist and their types.
  • Annotated: give the model extra meaning for each field.
  • Optional: the field may be missing. Include it only when it fits.
  • Literal: allow only specific words, such as pos or neg.
from typing import TypedDict, Annotated, Optional, Literal, List

class Review(TypedDict):
    key_themes: Annotated[List[str], "Write all the key themes"]
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[
        Literal["pos", "neg", "neutral"],
        "Use pos, neg, or neutral",
    ]
    pros: Annotated[
        Optional[List[str]],
        "List of pros if the review has them",
    ]
388

Pydantic Basics

Pydantic is a library for data validation. It checks that data is correct, structured, and type safe at run time.

Teams use it a lot with FastAPI when building APIs. It is very useful for structured LLM output too.

from pydantic import BaseModel

class Student(BaseModel):
    name: str

new_student = {"name": "bishal"}
student = Student(**new_student)
print(student)

If name is missing or the wrong type, Pydantic raises an error instead of silently accepting bad data.

389

Defaults, Email, and Field

Pydantic can set defaults, mark optional fields, validate emails, and add constraints.

from pydantic import BaseModel, EmailStr, Field
from typing import Optional

class Student(BaseModel):
    name: str = "bishal"
    age: Optional[int] = None
    email: EmailStr
    cgpa: float = Field(
        gt=0,
        lt=10,
        description="CGPA between 0 and 10",
    )

new_student = {
    "age": 32,
    "email": "bishal@example.com",
    "cgpa": 8.5,
}
student = Student(**new_student)
print(student)

student_dict = dict(student)
print(student_dict["age"])

Field can set default values, constraints like gt and lt, descriptions, and regex style rules.

Pydantic is also smart about casting. If you pass the string "32" for an int field, it often converts it for you.

390

Structured Output with Pydantic

Pass a Pydantic model into with_structured_output. You get a validated object back, not only a dict.

from langchain_groq import ChatGroq
from dotenv import load_dotenv
from typing import Optional, Literal, List
from pydantic import BaseModel, Field

load_dotenv()

model = ChatGroq(model="llama-3.3-70b-versatile")

class Review(BaseModel):
    key_themes: List[str] = Field(description="Write all the key themes")
    summary: str = Field(description="A brief summary of the review")
    sentiment: Literal["pos", "neg"] = Field(
        description="Sentiment as pos or neg",
    )
    name: Optional[str] = Field(
        default=None,
        description="Reviewer name if present",
    )
    pros: Optional[List[str]] = Field(
        default=None,
        description="Pros as a list if present",
    )

structured_model = model.with_structured_output(Review)
result = structured_model.invoke(
    "This is a very good mobile. I give it 5 stars."
)
print(result.name)
print(result.summary)

Defaults help when the LLM misses a field. Validation catches bad shapes early.

391

JSON Schema Path

Use a JSON Schema when many languages must agree on one shape. Example: a React front end and a Python back end sharing the same contract. JSON is the common format.

from langchain_groq import ChatGroq
from dotenv import load_dotenv

load_dotenv()

model = ChatGroq(model="llama-3.3-70b-versatile")

review_schema = {
    "title": "Review",
    "description": "Schema for a product review",
    "type": "object",
    "properties": {
        "summary": {"type": "string"},
        "sentiment": {"type": "string"},
        "name": {"type": "string"},
    },
}

structured_model = model.with_structured_output(review_schema)
result = structured_model.invoke(
    "This is a very good mobile. I give it 5 stars."
)
print(result)

JSON Schema does not give you Pydantic style automatic conversion and rich Python validation by itself.

392

Which Format and Which Method

Format Use when Watch out
TypedDict You only need type hints and you trust the LLM No real validation. Used less often in production
Pydantic You need validation, defaults, and type conversion This is what you use most of the time
JSON Schema Many languages share one schema No automatic conversion like Pydantic

Inside with_structured_output, providers may use methods such as:

  1. JSON mode: ask the model to return JSON shaped data.
  2. Function calling: treat the schema like a tool call the model must fill.

Day 25 takeaways

  • Natural language is great, but APIs and databases need structured fields.
  • Use with_structured_output when the model supports it. Use parsers when it does not.
  • TypedDict hints shape. Pydantic validates. JSON Schema shares contracts across languages.
  • Annotated, Optional, and Literal guide richer review style schemas.
  • Prefer Pydantic for most LangChain structured output work.
