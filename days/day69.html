Recap Traditional RAG

Traditional RAG is a process of three steps. Retrieval. Augmented. Generation. The user gives a query. We retrieve docs. We add those docs to the query. The LLM generates a response. The cards below are those three names.

Retrieval

Find docs that look close to the query.

Augmented

Put the retrieved data and the query into the LLM.

Generation

The LLM writes the response.

Retrieval

The user gives a query. We take that query to the embedding model. It converts the data into vector data. We take that vector to the vector database. The vector database already has the data. We do a semantic search. This process is called retrieval. We will get some documents. The steps below are that retrieve path.

Retrieve

  1. Query The user asks a question.
  2. Embed The embedding model turns it into a vector.
  3. Search The vector database does a semantic search.
  4. Docs We get some retrieved documents.

The LLM Blindly Trusts the Docs

Where is the problem in traditional RAG? When we give the documentation to the LLM, the LLM blindly trusts it. If retrieval is a miss, generation still treats those docs as the answer. The table below is that trust.

What RAG did What the LLM does
It handed over some retrieved docs. It trusts them and replies from them.

Far Neighbor Documents

Like this. We have data of machine learning in the vector database, but we asked about LLM. The vector database still tries to give an answer. What it does is give some far, near miss. It might give documentation of a chatbot, or of random forest. The LLM will reply, because RAG gave it that answer. The cards below are that miss.

What is in the db

Machine learning documents.

What we asked

A question about LLM.

What comes back

Chatbot docs, or random forest docs.

917

Leave Policy and Parametric Data

Like in a business scenario. A user asks if there is a leave policy, but there is no answer in the store. The LLM might give a wrong answer, because the vector database is not able to give the answer, and it still gives the wrong doc. If traditional RAG does not have the data from the doc, it uses parametric data for the reply. That is knowledge already inside the model weights. It has a high chance of hallucination. This is where CRAG comes in.

918

CRAG Puts a Model Before the LLM

The big difference in CRAG is this. We do not directly send the retrieved docs to the LLM. We put a model before the LLM. It checks if the retrieved data we got is useful or not. CRAG does not assume the docs are right. This is done with the help of a retrieval evaluator. The picture below is that extra check.

919

Three Cases

There are three cases. The docs are relevant, not relevant, or partially relevant. If relevant, CRAG uses that. If not relevant, it might use tools like web search, then reply. If it is partially relevant, it sends the relevant data to the LLM, then uses web search to get the other data. This is how CRAG works. The table below is that branch.

Case What CRAG does
Relevant, correct Use the retrieved docs, after we refine them.
Not relevant, incorrect Do not trust those docs. Use web search, then reply.
Partially relevant, ambiguous Keep the useful retrieved data, and also search the web.

We get that extra data because of chunking. That is why we need knowledge refinement. We do this with d1, then d2, then d3, and so on. The graph becomes START, retrieve, refine, generate, END. Decompose, Filter, Recompose

Knowledge refinement has three steps. Decomposition, filter, recomposition. Decomposition means dividing the document that we retrieved into sentences. These are called strips. Filter means we send the query plus the strips. We check each strip, which are important and which are not. Recomposition means now we have the important strips. We join them back to a document. That is merge them. The steps below are that clean up.

Refine one doc

  1. Decompose Cut the retrieved doc into sentence strips.
  2. Filter Query plus strips. Keep the important strips.
  3. Recompose Join the kept strips back into one document.

Retrieval Evaluation

The second improvement is retrieval evaluation. That is iteration 2. We will check if the retrieval is correct, ambiguous, that is partial, or incorrect. We will use an LLM for it. First we give d1, then d2, and so on. Each doc gets a score. We also store why each doc is given that score. The cards below are those three labels.

Correct

The retrieved docs are relevant.

Ambiguous

Partial. Some of the docs help.

Incorrect

The retrieved docs are not useful.

924

Thresholds 0.3 and 0.7

We will give them a threshold. Lower is 0.3. Higher is 0.7. First condition, if the score is greater than 0.7, that doc is correct. Second, if the score is less than 0.3, that doc is incorrect. Third, if the score is between 0.3 and 0.7, that doc is partial. We can set the threshold based on us. Let us suppose we have d1, d2, and d3. d1 is 0.8. d2 is 0.4. d3 is 0.2. If any of the documents is greater than the higher threshold, the retrieval is correct. Here d1 is 0.8, so the verdict is correct. But we will not use all docs for generation. We will only use d1 and d2, since d2 is partial, and d3 is below 0.3. The table below is that scoring.

Doc Score Label Keep for generate
d1 0.8 Correct, above 0.7 Yes.
d2 0.4 Partial, between 0.3 and 0.7 Yes.
d3 0.2 Incorrect, below 0.3 No.

Web Search When Incorrect

If the retrieval is incorrect, add a web search tool. We also need filtering, because the web search tool also gives multiple docs. So we need to refine them. Like strip them, filter them, then rejoin. Same three refine steps, now on the web docs. The table below is that extra clean up.

From the vector store From web search
Refine the retrieved chunks when they are useful. Refine the web docs too. Strip, filter, rejoin.
927

Query Rewrite

Iteration 4 is query rewrite. We do not search the query directly. We improve the query. The user query can be vague, underspecified, missing keywords, missing time constraint. So this iteration is very important. This is done in the incorrect path. Do this with the help of an LLM. Then web search uses that better query. The steps below are that rewrite.

Incorrect path

  1. Incorrect The retrieved docs are not useful.
  2. Rewrite The LLM improves the vague query.
  3. Web search Search with the new query. Then refine those docs.
928

Handling Ambiguity

Iteration 5 is handling ambiguity. Let us suppose we have multiple docs like d1, d2, d3. We will take all the docs that are more than 0.3, and all the docs given by the web search. So the generator sees the refined internal knowledge and the external web knowledge together. The table below is what each path sends.

Path What the generator gets
Correct The query plus refined internal knowledge.
Ambiguous The query plus internal knowledge plus web knowledge.
Incorrect The query plus web knowledge.

The Full CRAG Picture

Here is the full CRAG flow. Retrieval gets d1 and d2. The retrieval evaluator asks if those docs are correct for the query. Correct goes to knowledge refinement only. That path decomposes into strips, filters, then recomposes into internal knowledge. Incorrect rewrites the query, searches the web, then selects external knowledge. Ambiguous uses both. Day 69 takeaways

Day 69 takeaways

  • Traditional RAG is retrieval, then augment, then generation. The LLM blindly trusts the retrieved docs.
  • A far neighbor, like chatbot or random forest docs for an LLM question, still gets turned into a reply.
  • If the leave policy is missing, RAG may still hand a wrong doc, or the model may fall back to parametric data and hallucinate.
  • CRAG puts a retrieval evaluator before the LLM. Docs can be correct, ambiguous, or incorrect.
  • Knowledge refinement splits a doc into strips, filters them with the query, then joins the useful strips.
  • Scores use a low threshold of 0.3 and a high threshold of 0.7. Any doc above 0.7 can make the verdict correct. We still drop docs below 0.3.
  • Incorrect rewrites the query and searches the web. Ambiguous keeps docs above 0.3 and also uses the web docs.
