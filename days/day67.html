LLMs Have No Memory

Before we start, recall short term memory. An LLM does not have its own memory. It cannot remember the data. It is stateless. Every time we do llm.invoke, a fresh conversation starts. The table below is that fact.

What we might think What is true
The model keeps the last chat inside it. Each invoke is a new call. No past turns live in the weights.
879

Send Previous Messages

What we can do is this. We do not only send the user message. We also send the previous messages. Then the LLM has that past as context. Short term memory is also known as the conversation buffer. That buffer is the list we concat into the prompt.

880

Checkpointer and Threads

A checkpointer helps us implement short term memory. We store the state at every super step. We also implement threads. That is a thread id. With the thread id we can access the previous data. First we store it in RAM. Then we store it in a db. The steps below are that path.

How the buffer is kept

  1. Invoke The graph runs. Messages sit in MessagesState.
  2. Super step The checkpointer writes that state after the step.
  3. Thread id The same id loads the old buffer on the next invoke.
881

InMemorySaver Lives in RAM

We import InMemorySaver to store the data in RAM. We make a checkpointer. We can make a thread id. The problem is this. It is saved in RAM. RAM can be deleted, or the process can restart. Then the conversation is gone. The block below is that saver. Next we persist to a db.

InMemorySaver

from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()

Good for a demo. A restart wipes the buffer.

882

Save Threads in Postgres

PostgresSaver writes the checkpoint to Postgres. We compile the graph with that checkpointer. Each config has a thread id. Thread 1 and thread 2 are different buffers. We invoke Hello, how are you on thread 1. We invoke what is my name on thread 2. We print the last message content. We do not invent those two replies here. Run the file against your db to see them.

call_model takes MessagesState, calls the LLM on state messages, and returns a new message list. START goes to call_model. setup() prepares the tables. The blocks below are that graph and the two threads.

Graph and PostgresSaver

from langgraph.graph import StateGraph, START, MessagesState
from langgraph.checkpoint.postgres import PostgresSaver
from langchain_groq import ChatGroq
from dotenv import load_dotenv

load_dotenv()

llm = ChatGroq(model="openai/gpt-oss-20b", temperature=0)


def call_model(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}


builder = StateGraph(MessagesState)
builder.add_node("call_model", call_model)
builder.add_edge(START, "call_model")

DB_URI = "postgresql://postgres:postgres@localhost:15432/postgres"

Two threads

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()
    graph = builder.compile(checkpointer=checkpointer)

    t1 = {"configurable": {"thread_id": "thread-1"}}
    out1 = graph.invoke(
        {"messages": [{"role": "user", "content": "Hello, how are you?"}]},
        t1,
    )
    print("Thread1:", out1["messages"][-1].content)

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()
    graph = builder.compile(checkpointer=checkpointer)

    t2 = {"configurable": {"thread_id": "thread-2"}}
    out2 = graph.invoke(
        {"messages": [{"role": "user", "content": "what is my name"}]},
        t2
    )
    print("Thread2:", out2["messages"][-1].content)

Same db. Different thread ids. Thread 2 does not see thread 1.

Context Overflow

Every LLM has a context window. That shows how much context it can take at one time before maxing out. That is max tokens. If we go past it, the LLM might hallucinate. We cannot trust the LLM response. The input tokens should be way less than the context tokens.

Sometimes we send a very long input. We send the whole conversation as context. If the conversation is long, that concat can get bigger than the window. That is the context overflow problem. The table below is that risk.

Safe input Overflow
Input tokens stay well under the window. The full convo concat is bigger than max tokens.
The model can read what we sent. The model may hallucinate. We cannot trust the reply.
884

Trimming

Trimming is the first technique. We set a max token limit, like 500 tokens. Every time we send all the messages, we look at whether that send is less than 500 tokens, including the whole convo. If it exceeds, we trim. We keep the last n messages. We only take the messages whose total tokens are less than 500, and we drop the others from what the LLM sees. The idea is simple. Set max tokens. Only take the messages that fit. The steps below are that check.

Fit under 500

  1. Cap Set max tokens, such as 500.
  2. Count Count tokens on the messages we would send.
  3. Keep last If over the cap, keep the last messages that still fit.
885

trim_messages

We have a trim_messages function. We pass state messages. strategy is last. token_counter is count_tokens_approximately. max_tokens is 500. The role we give, like user, and the content, all get converted into tokens. If the previous message itself is more than the max tokens, it will only keep the current question. The block below is that call.

trim_messages

messages = trim_messages(
    state["messages"],
    strategy="last",
    token_counter=count_tokens_approximately,
    max_tokens=500,
)

strategy last means keep the newest turns that still fit under max_tokens.

886

We Do Not Delete

An important thing. In trimming we are not deleting the message. We are just not showing it to the LLM. The messages will still be in the state. The table below is that split.

In state Sent to the LLM
The full conversation buffer stays. Only the trimmed slice, under the token cap.
887

The Flaw in Trimming

Trimming has a flaw. It will take recent messages only and ignore the old messages. The LLM does not know if there is an older message. We might think we only need the recent convo. In the real world that goes wrong, because the old convo is necessary.

888

Summarization

The second technique is summarization. It works like trimming, but it is more advanced. We still send the recent messages. We do not ignore the old messages. We send the previous convo to the LLM and make a summary. So we send the summary of the previous convo, plus n recent convos, as context.

Like this. We have 500 convos. Only 100 of them fit under max tokens. We make a summary of the other 400 and send that to the LLM. This is why it is better than trimming. It preserves the context a bit. The table below is that pair.

Trimming Summarization
Keep last messages under the cap. Drop the rest from the prompt. Keep n recent turns. Summarize the older ones. Send both.
The LLM never sees the old turns. The LLM sees a short recap of the old turns.
889

Delete After We Summarize

In this technique we delete the previous conversation, since we already made the summary of it. First we have to delete it. We use RemoveMessage. The graph is START, then chat. If the check is true, we go to summarization, then END. If the check is false, we go to END. We need to check if the list in the state is greater than a number we pick, like 6 or 10. That number is n. The user defines it. If it is greater than 6, we make a summary. The picture below is that branch.

RemoveMessage

from langchain_core.messages import RemoveMessage

The name is RemoveMessage from langchain_core.messages. That is the working import.

First Summary, Then Update

Summary has a condition. We perform the summary the first time. If there is already a summary, we add that summary plus the new messages to make a new summary. We do not invent that update function here. The idea is: first write a summary, later fold new turns into it.

891

Day 67 takeaways

Day 67 takeaways

  • The LLM is stateless. Each invoke is a fresh call unless we send previous messages.
  • A checkpointer stores state each super step. A thread id reloads that conversation buffer.
  • InMemorySaver lives in RAM. PostgresSaver keeps threads in a db after a restart.
  • Input tokens should stay well under the context window, or the model may hallucinate.
  • Trimming keeps last messages under a cap. It does not delete them from state. Old turns are hidden from the LLM.
  • Summarization keeps recent turns and a recap of the rest. Then we delete the old turns with RemoveMessage.
  • If a summary already exists, fold it with the new messages into a new summary.
