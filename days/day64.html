HITL Is a Design Approach

Human in the loop, or HITL, is a design approach. We made AI agents for autonomy, so we do not have to work every step by hand. A customer support agent is that idea. The agent takes the easy tickets, and we save human time.

We still cannot depend on the AI alone. We keep a person in the middle for the final decision. The cards below are that split.

838

Help the Agent

Why does HITL exist? First, to help an agentic system. An LLM is not perfect today. We cannot trust it alone. It can get the wrong prompt. It can read a prompt in the wrong way. It can hallucinate. We take the help of a human for judgment.

839

Accountability

Second, we add accountability. AI systems are getting more powerful. An AI system cannot be accountable. So we keep a human in the loop. We need accountability for us.

A Gmail bot can read a mail and write a reply. It should not send that reply by itself. It should ask. We got this email. I wrote this reply. Should we send it?

Payment is the same idea. Many agents want to pay. A person still owns that yes.

Accuracy and Safety

HITL has two clear pluses. Human judgment raises the accuracy of the agent. It also raises safety. Say we tell a chatbot to delete files we have not used for 30 days. The agent should still ask before it deletes. Some of those files may still sit in a project. The cards below are those two pluses.

Accuracy

A person checks the draft or the plan, so fewer wrong actions go through.

Safety

A delete, a send, or a pay waits. The agent asks first.

Four HITL Patterns

These four patterns show up again and again. Action approval is approve or reject before the tool runs. Payment, email, and deletes sit here. Output review is look at the work after the agent finishes a draft. A research agent can research and write a post, then ask if it should post. Clarification is when the model is confused and asks a person. Escalation is when the agent cannot solve the problem, so it hands the case to a human. The cards below are those four.

A Social Media Manager

How does HITL work in LangGraph? Suppose we made a social media manager agent. It can write a tweet caption and post it. The user enters a topic. Then the agent researches. Then it posts. First it makes a caption. Second it posts.

Behind the scenes the simple graph is START, research, post, END. The user types a topic and clicks submit. That click invokes the graph. START gets the topic. Research helps find the info. Then we generate the tweet. Then post would put it live. The steps below are that path with no pause yet.

843

interrupt Pauses the Graph

HITL sits in the post step. We call interrupt. The graph looks at that call and pauses. It saves the current state in a checkpointer, such as a SQLite db. It prepares a message like I have made this draft, should I post it. That message goes to the front end. The user sees it and types yes or no. Then we invoke the graph again with a Command, and that Command carries yes or no.

In HITL the graph execution gets paused. The picture below is that pause, then the resume.

844

Draft Then Ask

The idea was research then post. The sample we write stays small. Two nodes. draft writes one short tweet. post calls interrupt and waits for yes or no. State holds topic, draft, and decision. The model is ChatOpenRouter. We do not invent a tweet here. Run the file to see the draft your model writes.

draft_node sends one prompt, then stores message.content in draft. If content is a list, we join the text parts. post_node is where we pause. interrupt gets the draft plus the ask. If the resume answer is yes, we print Posted and the draft. If not, we print Not posted. Then we save the answer in decision.

State and nodes

class State(TypedDict):
    topic: str
    draft: str
    decision: str


def draft_node(state: State):
    message = llm.invoke(
        f"Write one short tweet about {state['topic']}. Reply with only the tweet."
    )
    text = message.content
    if isinstance(text, list):
        text = "".join(
            part if isinstance(part, str) else part.get("text", "")
            for part in text
        )
    return {"draft": text}


def post_node(state: State):
    # pause here and wait for yes or no
    answer = interrupt(
        "Draft:\n" + state["draft"] + "\n\nPost it? Type yes or no."
    )

    if str(answer).strip().lower() == "yes":
        print("Posted:", state["draft"])
    else:
        print("Not posted.")

    return {"decision": str(answer)}

interrupt stops the node. The string we pass is what the front end can show.

845

Resume with Command

We add draft, then post. START goes to draft. draft goes to post. post goes to END. compile needs a checkpointer. This sample uses InMemorySaver. The idea we taught still holds. A checkpointer can be a SQLite db when you want the pause to survive a restart.

In main we ask for a topic. config uses thread_id so the pause and the resume share one thread. We stream the first input. When the event has __interrupt__, we print that value, read yes or no, then invoke with Command(resume=answer) and the same config. The blocks below are that graph and that loop.

Imports and model

from dotenv import load_dotenv
from typing import TypedDict

from langchain_openrouter import ChatOpenRouter
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, END, StateGraph
from langgraph.types import Command, interrupt

load_dotenv()

llm = ChatOpenRouter(
    model="openrouter/free",
    temperature=0,
)

Compile and resume

graph = StateGraph(State)
graph.add_node("draft", draft_node)
graph.add_node("post", post_node)
graph.add_edge(START, "draft")
graph.add_edge("draft", "post")
graph.add_edge("post", END)

app = graph.compile(checkpointer=InMemorySaver())


if __name__ == "__main__":
    topic = input("Topic: ")
    config = {"configurable": {"thread_id": "1"}}

    for event in app.stream({"topic": topic}, config):
        if "__interrupt__" in event:
            print(event["__interrupt__"][0].value)
            answer = input("yes or no: ")
            app.invoke(Command(resume=answer), config)

The first stream runs until interrupt. The Command call is the second invoke, on the same thread.

HITL in a Flight Chatbot

Example 2 puts HITL in a chatbot before a buy. The same idea as buying a share. The sample we write looks up a flight for free, and waits before it books. START goes to chat. From chat we can END, or go to tools. tools go back to chat. find_flight is the lookup. book_flight is the dummy book. The picture below is that loop.

find_flight returns a fixed next flight line. book_flight returns a booked line. Those strings are in the tool, not from a live airline. The system prompt says use find_flight to look up, and use book_flight only when the user wants to book.

Two tools

@tool
def find_flight(city: str) -> str:
    """Find the next flight time and price for a city."""
    return f"Next flight to {city} is at 10:00 AM. Price is $200."


@tool
def book_flight(city: str) -> str:
    """Book a flight to a city."""
    return f"Booked the flight to {city}."


tools = [find_flight, book_flight]
tools_by_name = {item.name: item for item in tools}
llm_with_tools = llm.bind_tools(tools)

Lookup and book are both tools. Only book trips the pause inside tool_node.

847

tool_node Waits to Book

chat_node prepends a SystemMessage, then calls llm_with_tools. tool_node reads the last message. If any tool call is book_flight, we interrupt and ask Book this flight? Type yes or no. Lookup is free. Booking waits for a person. If the answer is not yes, we send a ToolMessage for each call that says the user said no. If the answer is yes, we run the tools and send those results back. Then the edge goes to chat again.

as_text turns a list content into one string. chat_node puts a SystemMessage first, then the chat history, then invokes llm_with_tools. ask streams the graph. On __interrupt__ it prints the value, reads yes or no, and calls ask again with Command(resume=answer). When there is no interrupt, it prints the last message as text. The main loop reads You until quit or exit. The blocks below are those pieces.

chat_node

def as_text(content):
    if isinstance(content, list):
        return "".join(
            part if isinstance(part, str) else part.get("text", "")
            for part in content
        )
    return content


def chat_node(state: MessagesState):
    messages = [
        SystemMessage(
            content=(
                "You help with flights. "
                "Use find_flight to look up a flight. "
                "Use book_flight only when the user wants to book."
            )
        ),
        *state["messages"],
    ]
    return {"messages": [llm_with_tools.invoke(messages)]}

The star unpacks the old messages after the system line.

tool_node

def tool_node(state: MessagesState):
    last = state["messages"][-1]
    wants_to_book = any(call["name"] == "book_flight" for call in last.tool_calls)

    # look up is free. booking waits for a person.
    if wants_to_book:
        answer = interrupt("Book this flight? Type yes or no.")
        if str(answer).strip().lower() != "yes":
            return {
                "messages": [
                    ToolMessage(
                        content="The user said no. Do not book.",
                        tool_call_id=call["id"],
                    )
                    for call in last.tool_calls
                ]
            }

    messages = []
    for call in last.tool_calls:
        result = tools_by_name[call["name"]].invoke(call["args"])
        messages.append(
            ToolMessage(content=str(result), tool_call_id=call["id"])
        )
    return {"messages": messages}

find_flight never hits interrupt. book_flight does, before invoke.

Graph and ask

graph = StateGraph(MessagesState)
graph.add_node("chat", chat_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "chat")
graph.add_conditional_edges("chat", tools_condition)
graph.add_edge("tools", "chat")

app = graph.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "1"}}


def ask(graph_input):
    for event in app.stream(graph_input, config):
        if "__interrupt__" in event:
            print(event["__interrupt__"][0].value)
            answer = input("yes or no: ")
            ask(Command(resume=answer))
            return

    last = app.get_state(config).values["messages"][-1]
    print("Bot:", as_text(last.content))

tools_condition sends tool calls to the tools node. A no still returns ToolMessages so chat can talk again.

Imports and the chat loop

from dotenv import load_dotenv

from langchain_core.messages import HumanMessage, SystemMessage, ToolMessage
from langchain_core.tools import tool
from langchain_openrouter import ChatOpenRouter
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, MessagesState, StateGraph
from langgraph.prebuilt import tools_condition
from langgraph.types import Command, interrupt

if __name__ == "__main__":
    print("Ask about a flight. Type quit to stop.")
    while True:
        text = input("You: ").strip()
        if text.lower() in {"quit", "exit"}:
            break
        if text:
            ask({"messages": [HumanMessage(content=text)]})

Day 64 takeaways

  • HITL is a design approach. Agents can look up. A person still owns the last yes.
  • We keep HITL because models err, and because an AI cannot be accountable.
  • Accuracy and safety go up. A delete, a send, or a pay can wait.
  • Common patterns are action approval, output review, clarification, and escalation.
  • interrupt pauses the graph, saves state in a checkpointer, and asks the front end.
  • We resume with Command and the same thread. yes posts or books. Anything else stops.
  • In the chatbot, find_flight is free. book_flight waits inside tool_node.
