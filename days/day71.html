Vibe Testing

We say we tested. We asked a question. We got an answer. We think the agent is working. That testing is called vibe testing. Vibe testing means we test an LLM app casually with a few prompts, and we judge it by feel. It is informal, subjective, and usually not repeatable. It only works at the personal project level. For production we need LLM evals. The cards below are that gap.

Casual

Air Canada Chatbot

A person's grandmother died. The user asked the Air Canada chatbot if they would get any discount for urgent travel. The chatbot hallucinated. It replied, first pay, then we will refund you. The actual policy was the opposite. The person should get the discount first. There is no later refund. Staff said no, there is no such thing. The user was not happy, so they sued. The court said the chatbot is company property, so the company should pay. The company got a lot of backlash. The flow below is that case.

What happened

  1. Ask Urgent travel after a death. Will I get a discount?
  2. Hallucinate Pay first. We will refund you later.
  3. Real policy Discount first. No later refund. Staff said no.
  4. Court The chatbot is company property. The company should pay.

953

Why We Skip Evals

We might think, if LLM evaluation is this important, why do we not do it often? The main answer is it is not that straight. LLM based applications are tricky to evaluate. The next lessons show why software apps are easier, and why LLM apps need a different kind of test.

954

Software Apps vs LLM Apps

A software based app is deterministic. For a given input, the output is always the same. An LLM based app is non deterministic. By nature it is probabilistic. Every answer can be different. It can give one answer this time, a different answer in six months, and another answer after that. That is why software based evaluation is much easier than LLM based evaluation. The table below is that split.

Software based app LLM based app
Deterministic. Same input, same output. Non deterministic. Probabilistic by nature.
The answer stays the same later. This time one answer. In six months a different answer.
The benchmark is correctness. Is 2 plus 2 equal to 4? We need multi dimensional checks, not one score.
955

Multi Dimensional Checks

In software we only look if 2 plus 2 is 4. In an LLM based app we need a multi dimensional check. We can evaluate fact check, tonality, how much time it took to give the answer, and how much it cost. What we check is different from application to application. The cards below are those dimensions.

Fact check

Is the answer true, or did the model make it up?

Tonality

Is the tone right for this user and this product?

Latency

How much time did it take to give the answer?

Cost

How much did that answer cost to run?

956

What LLM Evals Are

LLM evals are systematic, repeatable, replicable tests used to judge an LLM or an LLM powered system against clear criteria. The main things are these three. They are systematic. They are repeatable. They have clear criteria. Without those, we are just vibe testing again.

957

Systematic, Repeatable, Clear Criteria

Systematic means we are not doing vibe testing. We create a proper dataset. We cover every edge case for a proper test of the LLM based system. We test based on 100 real use chat queries from that dataset. Repeatable means even if we change everything, the model, the prompt, the retriever, the test should still work the same way. That is how we find which version is working. Clear criteria means we name what good looks like. Correct. Simple explain. Grounded content. Safe. Policy compliant. Without criteria we are just vibe testing. The cards below are those three.

Systematic

A proper dataset. Edge cases. 100 real use chat queries.

Repeatable

Change the model, prompt, or retriever. Run the same test. Compare versions.

Clear criteria

Correct. Simple explain. Grounded. Safe. Policy compliant.

958

Evals Are the Whole Setup

Important notice. Evals are not just metrics. They are not only numbers. Evals mean the complete test setup for testing the LLM. What are we evaluating, like the retriever? What does good mean, like the accuracy of the retriever? When are we running the test, like online or in production? Which tools are we using, like Ragas? So LLM evals are the whole setup for testing. What we are testing. Where. How. Why. Which tools. The steps below are that setup.

The setup

  1. What What are we evaluating? The retriever, the answer, the whole app?
  2. Good means What does good mean? Accuracy of the retriever, for example.
  3. When When do we run the test? Online, or in production?
  4. Which tools Which tools are we using? Ragas is one example.

The Goal of Evals

The goal of LLM evals is not scoring. A score is not the point. Evals give the answer to a particular question. Can the model be used for a particular task or application? Is the system good enough to ship? Is it safe for the user? The cards below are those questions.

Can we use this model?

Can it do this particular task or application?

Good enough to ship?

Is the system ready for production users?

Safe for the user?

Will it harm people with a wrong or unsafe answer?

LLM evals have two types. Model evals and application evals. Disclaimer. Model evals and application evals are not the real terms. We are using them anyway. Model evals are the kind of evals where we evaluate the LLM. Application evals are the kind of evals where we evaluate the LLM based application. The cards below are that split.

961

Model Evals

Model evals evaluate the model itself. The main idea is to test and evaluate the capabilities of a model. Like GPT vs Claude vs Gemini. We use a benchmark to check if it works well. We find how capable the LLM is. All of this is done with the help of the benchmark. As an AI engineer we usually do not work on model evals. We just need to learn what model evals are, what a benchmark is, and how to read the benchmark. That still matters. When we make an LLM based application we need to select the LLM. We can select it based on the benchmark. We feel more literate.

How We Read Benchmarks

For knowledge and reasoning we use the MMLU benchmark. It asks subject and reasoning questions across domains like science, history, law, and medicine. For coding we use SWE bench and HumanEval. We do not have to build these tests ourselves. We need to read them when we pick a model. The table below is that map.

What we check Benchmark
Knowledge and reasoning across domains. MMLU. Science, history, law, medicine, and more.
Coding. SWE bench. HumanEval.

Application Evals

This is the most important kind for the AI engineer. An LLM application does not mean everything important is the LLM. The LLM is important, but we need other important things as well. Prompt layer. Tools like an API. Orchestration workflow. Guardrails. Output parser. For RAG, retrieval, embedding model, vector database. Monitoring. Logging. Feedback loop. Application evals assess the behavior and performance of an LLM based app, whether at the level of the entire system, or a system component within it. The cards below are those extra pieces.

The Smartphone Analogy

The best analogy is a smartphone. We have chips. The chip has a benchmark, so we find which processor is strong. But a strong processor does not mean the phone is good. We need a good OS, camera, sound, graphics card, and the rest. If all of those work, then the smartphone works well. So we need to test all those components as well. In application evals we ask, does the product work? Is the question answered? Is the answer faithful? Is it safe? Is it fast? The steps below are that analogy.

Phone vs app

  1. Chip The LLM has a benchmark. A strong model is not the whole product.
  2. The rest OS, camera, sound, graphics. Prompt, tools, RAG, guardrails.
  3. Does it work? Answered. Faithful. Safe. Fast.

Day 71 takeaways

Day 71 takeaways

  • Vibe testing is a few prompts judged by feel. Informal, subjective, usually not repeatable. Fine for a personal project. Not for production.
  • Air Canada, Chevrolet, and fake court cases show why evals matter. Hallucination and jailbreak can reach users, courts, and social media.
  • Software apps are deterministic. LLM apps are non deterministic. We check facts, tone, latency, and cost, not only correctness.
  • LLM evals are systematic, repeatable tests against clear criteria. They are the whole setup, not only a number.
  • Model evals read benchmarks like MMLU, SWE bench, and HumanEval so we can pick a model. Application evals test the product, because a strong LLM is not a strong app.
